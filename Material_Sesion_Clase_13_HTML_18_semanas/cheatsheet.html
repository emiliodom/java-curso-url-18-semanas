Login, roles y variables de entorno: todo en una página

Continúa Jugador en taller-formularios (Escuela de Fútbol Los Cerritos). Tema nuevo: quién puede entrar y qué puede hacer.

Autenticación vs. autorización

PreguntaAnalogía escolarEn el proyecto
Autenticación¿Quién eres?La llave que demuestra que eres docente de la escuelaEl login: usuario y contraseña
Autorización¿Qué puedes hacer?La llave del aula no abre la dirección; el director firma el libro de calificacionesRoles ADMIN y ENTRENADOR

El flujo del login en 5 pasos

  1. La persona escribe usuario y contraseña en login.html (campos llamados username y password).
  2. Spring Security llama a UsuarioDetailsService.loadUserByUsername(...): "dame los datos de este usuario".
  3. El servicio busca en la base con UsuarioRepository.findByUsername(...).
  4. Spring compara lo escrito con el hash BCrypt guardado (no desencripta: vuelve a calcular y compara).
  5. Coincide: entra con su rol y va a /jugadores. No coincide: /login?error.

Hash (BCrypt) vs. cifrar

CifrarHash (BCrypt)
AnalogíaCaja con candadoLicuadora: de la fruta sale jugo, del jugo no vuelves a la fruta
¿Se puede revertir?Sí, con la llaveNo

En la tabla usuario la columna password contiene algo como $2a$10$..., nunca Clave-Admin-2026. La misma clave produce un hash distinto cada vez; PasswordEncoder sabe compararlos. Se crea con passwordEncoder.encode(clave).

Variables de entorno: el post-it que no se pega al monitor

Escribir la contraseña en el código es pegar el post-it con la clave en el monitor (y GitHub es público). Con una variable de entorno el archivo solo tiene un hueco, ${NOMBRE}, y la clave se entrega al arrancar.

# src/main/resources/application.properties
app.admin.password=${ADMIN_PASSWORD}
app.entrenador.password=${ENTRENADOR_PASSWORD}
# PowerShell (Windows)
$env:ADMIN_PASSWORD = "Clave-Admin-2026"
$env:ENTRENADOR_PASSWORD = "Clave-Entr-2026"
.\mvnw.cmd spring-boot:run

# Git Bash / macOS / Linux
export ADMIN_PASSWORD="Clave-Admin-2026"
export ENTRENADOR_PASSWORD="Clave-Entr-2026"
./mvnw spring-boot:run
  • Esas claves son ejemplo: usa las tuyas.
  • Viven solo en esa ventana de terminal: si la cierras, defínelas otra vez.
  • Esta semana arranca desde la terminal: el botón ▶ Run de VS Code no ve las variables de la terminal.
  • CargadorUsuarios solo crea los usuarios si no existen: cambiar la variable después no cambia la clave ya guardada. En desarrollo, detén la app y borra la carpeta datos/ (pierdes los jugadores).
  • En la Semana 14 se repite con DB_URL, DB_USER y DB_PASSWORD de Neon.

Roles y reglas de acceso

.requestMatchers("/login", "/estilos.css", "/error").permitAll()
.requestMatchers("/jugadores/nuevo", "/jugadores/*/editar").hasRole("ADMIN")
.requestMatchers(HttpMethod.POST, "/jugadores/**").hasRole("ADMIN")
.anyRequest().authenticated()
RutaQuién entra
/login, /estilos.css, /errorTodos (públicas)
GET /jugadores/nuevo, GET /jugadores/*/editar, todo POST a /jugadores/**Solo ADMIN
Cualquier otra (/, /jugadores)Cualquier usuario con sesión

El orden importa: gana la primera regla que coincide, y anyRequest() va al final. Los roles se guardan sin el prefijo (ADMIN); Spring agrega ROLE_ solo.

sec:authorize vs. requestMatchers

sec:authorizerequestMatchers
DóndeEn la plantilla (lista.html)En SecurityConfig
Qué decideQué se dibuja (botón, columna)Qué se permite (la ruta)
Si lo omitesEl entrenador ve botones que no puede usarEl entrenador entra a /jugadores/nuevo escribiendo la dirección
<html lang="es" xmlns:th="http://www.thymeleaf.org"
      xmlns:sec="http://www.thymeleaf.org/extras/spring-security">
<p sec:authorize="hasRole('ADMIN')"><a th:href="@{/jugadores/nuevo}">+ Inscribir jugador</a></p>
<strong sec:authentication="name">usuario</strong>
<form th:action="@{/logout}" method="post"><button type="submit">Cerrar sesión</button></form>

Ocultar un botón NO protege la ruta. Ocultar mejora la experiencia; requestMatchers da la seguridad. Úsalos juntos. El cierre de sesión es un POST con token: th:action lo agrega solo.

Validaciones reducidas (solo nombre y edad)

CampoReglasMensaje
nombre@NotBlank"El nombre es obligatorio."
edad (Integer)@NotNull, @Min(5), @Max(17)"La edad es obligatoria." / "La edad mínima es 5 años." / "La edad máxima es 17 años."
  • Todas vienen de jakarta.validation.constraints (NotBlank, NotNull, Min, Max), con su import cada una.
  • Campo numérico = Integer, no int (con int, la casilla vacía da un error en inglés).
  • Con errores se devuelve la plantilla (no redirect); con éxito: guardar → redirigir → mostrar.
  • Si falta spring-boot-starter-validation, las reglas se ignoran en silencio.
Datos sensibles: nunca a GitHub
Contraseñas de usuarios, DB_URL/DB_USER/DB_PASSWORD de Neon, tokens o claves de API, la carpeta datos/ (contiene jugadores, menores de edad) y correos o teléfonos reales de encargados. No son sensibles: nombre del proyecto, código sin secretos, nombres de clases y estilos.
