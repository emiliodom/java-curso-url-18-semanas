Proyecto · Entregable de la Guía de Aprendizaje 13 (1 pt)

Tu proyecto guarda datos y ahora tiene puerta con llave

Primero la guía paso a paso para comprobar que todo tu proyecto guarda datos y para construir el login con dos roles; al final, la plantilla calificable. Fecha límite: antes de la Sesión 14.
Antes de empezar
Necesitas tu proyecto real de la Semana 12: la entidad de tu institución con su repositorio, su servicio, su controlador, sus plantillas y la base H2 en archivo (jdbc:h2:file:./datos/...). Esta guía continúa ese mismo proyecto: no empieces uno nuevo. En todo el código de esta página, TuEntidad (o tuentidad) es el nombre de la clase de tu proyecto y gt.edu.url.tuproyecto es tu paquete base. El ejemplo de la clase (Jugador, Escuela de Fútbol Los Cerritos) solo sirve de referencia: tú usas tus nombres. Cómo se llaman los tres nombres derivados de tu Artifact (carpeta, paquete, clase principal) está explicado en el Cheat Sheet.
Esta guía vale 1 punto y no es Entrega Parcial
Es la Guía 13 (1 pt). La siguiente entrega con peso extra es la Entrega Parcial 3, en la Semana 14, donde publicarás todo esto en Render y Neon. Por eso hoy dejas lista la parte difícil: que las contraseñas no estén escritas en el código.
Qué vas a lograr, con una analogía de colegio
Hasta la Semana 12 tu aplicación era un salón sin puerta: cualquiera entraba y podía borrar la lista de asistencia. Hoy le pones puerta con llave (autenticación: demostrar quién eres) y decides quién puede hacer qué (autorización: el director puede cambiar notas; el docente de turno solo las consulta). Y las llaves no se dejan pegadas en el monitor (la contraseña no se escribe en el código): se entregan aparte, con variables de entorno.

Parte guiada — completa tu proyecto y ponle login

Paso 0 — Trabaja en una rama

Estos cambios tocan muchos archivos. Si algo sale mal, quieres poder volver atrás sin perder lo que ya funcionaba. Trabaja en la rama development de tu repositorio (la misma de las semanas anteriores):

git checkout development
git pull
git status

¿No recuerdas cómo era? Repasa la Semana 4 (ramas). Si tu rama de trabajo tiene otro nombre, úsala; lo importante es no trabajar directamente en main.

✅ Checkpoint: git status dice On branch development y no hay cambios sin guardar.

Paso 1 — Comprueba que TODO tu proyecto guarda datos Repaso de Semana 12

Antes de agregar nada nuevo, asegúrate de que la base está sana. Un login sobre una aplicación que pierde datos no sirve de nada. Arranca tu proyecto y haz esta ronda completa con tu entidad:

  1. Crear: registra 3 elementos reales de tu institución.
  2. Listar: comprueba que los 3 salen en la tabla.
  3. Editar: cambia uno y verifica que no se duplica.
  4. Eliminar: borra uno.
  5. Reinicio: detén la aplicación (Ctrl+C en la terminal), arráncala de nuevo y verifica que los que quedaron siguen ahí.

Revisa también tu application-dev.properties. Las dos líneas que hacen sobrevivir los datos son:

spring.datasource.url=jdbc:h2:file:./datos/tubasededatos
spring.jpa.hibernate.ddl-auto=update

Si tus datos desaparecen al reiniciar, la URL dice mem en lugar de file, o ddl-auto es create. Corrige y repite la prueba antes de seguir.

✅ Checkpoint: crear, listar, editar y eliminar funcionan, y los datos siguen ahí después de reiniciar.

Paso 2 — Deja solo 2 validaciones en tu entidad Simplifica lo de la Semana 11

Esta semana no se trata de validar, así que mantén lo mínimo: dos campos con mensajes claros. Elige los dos que más importan en tu institución (en el ejemplo: nombre y edad). El resto de tus campos puede conservar validaciones si ya las tienes funcionando; no las repases hoy. Ejemplo de forma, adaptado a campos de tu entidad:

// src/main/java/gt/edu/url/tuproyecto/model/TuEntidad.java  (solo las líneas de validación)
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

    @NotBlank(message = "El nombre es obligatorio.")
    private String nombre;

    @NotNull(message = "La edad es obligatoria.")
    @Min(value = 5, message = "La edad mínima es 5 años.")
    @Max(value = 17, message = "La edad máxima es 17 años.")
    private Integer edad;
  • El campo numérico es Integer, no int (casilla vacía = null, no un error en inglés).
  • Recuerda: es jakarta, no javax.
  • Tu controlador conserva el patrón: con errores devuelve la plantilla; con éxito, guardar → redirigir → mostrar.
✅ Checkpoint: enviar el formulario vacío muestra tus dos mensajes y no guarda nada.

Paso 3 — Agrega las dependencias de seguridad Nuevas en Semana 13 Imprescindible

Necesitas dos dependencias nuevas en tu pom.xml, sin escribir versión (Spring Boot la elige). Pégalas dentro de <dependencies>, junto a las demás, sin duplicar nada y sin borrar nada:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

<dependency>
    <groupId>org.thymeleaf.extras</groupId>
    <artifactId>thymeleaf-extras-springsecurity6</artifactId>
</dependency>
  • spring-boot-starter-security: el sistema de login y de permisos.
  • thymeleaf-extras-springsecurity6: permite escribir sec:authorize en las plantillas para mostrar u ocultar partes de la página según el rol.
Si algún día generas un proyecto nuevo en start.spring.io, marcar Spring Security junto con Thymeleaf agrega ambas solas. Aquí, como continúas tu proyecto, las agregas a mano. Recarga Maven (VS Code ofrece "Sync/Reload") después de editar.
Cuidado con la falla silenciosa
Sin la segunda dependencia el proyecto compila y arranca, pero sec:authorize simplemente no se procesa y los botones no se ocultan (no aparece ningún error). Si "los botones no se ocultan", revisa primero que esta dependencia exista.
✅ Checkpoint: el proyecto arranca. En la consola aparece Using generated security password: ... y, al abrir http://localhost:8080, el navegador te pide usuario y contraseña. Es el login por defecto de Spring (usuario user): esa pantalla confirma que Security está activa. Hoy la reemplazas por la tuya.

Paso 4 — Crea la entidad Usuario y su repositorio Archivos nuevos

Los usuarios viven en la misma base que tus datos, en una tabla propia. Dos archivos, igual que en la Semana 12. Qué cambia respecto al ejemplo de la clase: únicamente la línea package y los import que llevan tu paquete base. Qué NO cambia: el nombre Usuario, sus tres campos y findByUsername (Spring Security espera justo esa forma).

// src/main/java/gt/edu/url/tuproyecto/model/Usuario.java
package gt.edu.url.tuproyecto.model;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Usuario {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String username;

    // Aquí NUNCA va la contraseña real: va el "hash" que produce BCrypt.
    @Column(nullable = false)
    private String password;

    // "ADMIN" o "ENTRENADOR" (sin el prefijo ROLE_; Spring lo agrega solo).
    // En tu proyecto puedes usar los nombres de rol que tengan sentido
    // (por ejemplo "COORDINADOR" y "VOLUNTARIO"), en MAYÚSCULAS y sin espacios.
    @Column(nullable = false)
    private String rol;

    public Usuario() {
    }

    public Usuario(String username, String password, String rol) {
        this.username = username;
        this.password = password;
        this.rol = rol;
    }

    public Long getId() { return id; }
    public String getUsername() { return username; }
    public String getPassword() { return password; }
    public String getRol() { return rol; }
}
// src/main/java/gt/edu/url/tuproyecto/repository/UsuarioRepository.java
package gt.edu.url.tuproyecto.repository;

import java.util.Optional;

import org.springframework.data.jpa.repository.JpaRepository;

import gt.edu.url.tuproyecto.model.Usuario;

public interface UsuarioRepository extends JpaRepository<Usuario, Long> {

    Optional<Usuario> findByUsername(String username);
}
findByUsername es un método derivado por nombre (Semana 12): Spring lo implementa solo porque la entidad tiene un campo llamado username. Devuelve Optional porque el usuario puede no existir.
✅ Checkpoint: ambos archivos sin subrayado rojo, Usuario en model y UsuarioRepository en repository (dentro de tu paquete base, no fuera).

Paso 5 — Las contraseñas entran por variables de entorno Edita application.properties Nunca escribas la clave real

Una variable de entorno es un dato que vive en la computadora (o en el hosting), fuera de tus archivos. Es como entregarle la llave al director en la mano en lugar de pegarla en un post-it en el monitor, donde cualquiera que mire el repositorio público la vería. Agrega al final de tu src/main/resources/application.properties:

# Contraseñas iniciales: NO están escritas aquí. Se leen de variables de entorno.
app.admin.password=${ADMIN_PASSWORD}
app.entrenador.password=${ENTRENADOR_PASSWORD}

Cada ${...} es un hueco que Spring llena con la variable de ese nombre. Antes de arrancar, define tus propias claves (inventa unas que no uses en ningún otro lugar; las de abajo son solo ejemplo) en la misma terminal desde la que vas a arrancar la aplicación:

# PowerShell (Windows)
$env:ADMIN_PASSWORD = "Clave-Admin-2026"
$env:ENTRENADOR_PASSWORD = "Clave-Entr-2026"
.\mvnw.cmd spring-boot:run
# Git Bash / macOS / Linux
export ADMIN_PASSWORD="Clave-Admin-2026"
export ENTRENADOR_PASSWORD="Clave-Entr-2026"
./mvnw spring-boot:run
Esta semana arranca desde la terminal, no con el botón ▶ Run de VS Code: ese botón no ve las variables definidas en tu terminal. Las variables viven solo en esa ventana: si la cierras, hay que definirlas otra vez. Para reiniciar, Ctrl+C y el mismo comando.
Si falta una variable, la aplicación se niega a arrancar (y está bien)
Verás PlaceholderResolutionException: Could not resolve placeholder 'ADMIN_PASSWORD'. Es preferible que falle a que quede un administrador sin contraseña. Define la variable y vuelve a arrancar.
✅ Checkpoint: tu application.properties contiene ${ADMIN_PASSWORD} y ${ENTRENADOR_PASSWORD}, y ninguna contraseña real escrita.

Paso 6 — Crea la carpeta security con sus tres clases Carpeta nueva Debe quedar dentro del paquete base

Carpeta nueva security, hermana de model, repository, service y controller. Como en la Semana 9: si queda fuera de tu paquete base, Spring no la encuentra y no avisa.

En cada archivo de esta carpeta¿Qué haces?
Línea package y los import gt.edu.url...Cambian: pon tu paquete base.
Rutas de SecurityConfig (/RUTA/...)Cambian: tu ruta real (en el ejemplo de la clase es /jugadores).
Nombres de roles y de usuarios (ADMIN, admin...)Pueden cambiar, pero deben ser idénticos en SecurityConfig, CargadorUsuarios y las plantillas.
Anotaciones, BCryptPasswordEncoder, findByUsername, User.withUsername, el orden de las reglasNO cambian: son la mecánica de Spring Security.

6a. UsuarioDetailsService — cuando alguien intenta entrar, Spring Security pregunta aquí: "dame los datos del usuario que se llama así". Es como la lista de asistencia: busca el nombre y devuelve la ficha.

// src/main/java/gt/edu/url/tuproyecto/security/UsuarioDetailsService.java
package gt.edu.url.tuproyecto.security;

import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

import gt.edu.url.tuproyecto.model.Usuario;
import gt.edu.url.tuproyecto.repository.UsuarioRepository;

@Service
public class UsuarioDetailsService implements UserDetailsService {

    private final UsuarioRepository usuarioRepository;

    public UsuarioDetailsService(UsuarioRepository usuarioRepository) {
        this.usuarioRepository = usuarioRepository;
    }

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        Usuario usuario = usuarioRepository.findByUsername(username)
                .orElseThrow(() -> new UsernameNotFoundException("Usuario no encontrado: " + username));

        return User.withUsername(usuario.getUsername())
                .password(usuario.getPassword())
                .roles(usuario.getRol())
                .build();
    }
}

6b. SecurityConfig — el reglamento de la puerta: qué rutas son públicas, cuáles exigen rol y cómo se cifran las contraseñas. Gana la primera regla que coincide, por eso las específicas van arriba y anyRequest() al final.

// src/main/java/gt/edu/url/tuproyecto/security/SecurityConfig.java
package gt.edu.url.tuproyecto.security;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    public SecurityFilterChain filtros(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(reglas -> reglas
                // Gana la PRIMERA regla que coincide: el orden importa.
                .requestMatchers("/login", "/estilos.css", "/error").permitAll()
                .requestMatchers("/RUTA/nuevo", "/RUTA/*/editar").hasRole("ADMIN")
                .requestMatchers(HttpMethod.POST, "/RUTA/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .formLogin(login -> login
                .loginPage("/login")
                .defaultSuccessUrl("/RUTA", true))
            .logout(logout -> logout
                .logoutSuccessUrl("/login?salio"))
            .exceptionHandling(errores -> errores
                .accessDeniedPage("/acceso-denegado"));
        return http.build();
    }
}
  • Sustituye /RUTA por la ruta base que ya usa tu controlador (la que escribiste con @GetMapping en la Semana 12). Aparece en tres líneas.
  • /estilos.css: si tu archivo de estilos tiene otro nombre o está en otra carpeta de static/, cambia esa ruta; si no es pública, la página de login saldrá sin estilo.
  • Con este reglamento: ver la lista y las demás rutas = cualquier usuario con sesión; crear, editar y eliminar (todo POST a tu ruta) = solo ADMIN.
  • Contraseñas guardadas como hash BCrypt (empiezan con $2a$), nunca en texto plano.

6c. CargadorUsuarios — se ejecuta una vez al arrancar y crea los dos usuarios solo si todavía no existen. Lee las claves de las variables de entorno y las cifra antes de guardarlas.

// src/main/java/gt/edu/url/tuproyecto/security/CargadorUsuarios.java
package gt.edu.url.tuproyecto.security;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.CommandLineRunner;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Component;

import gt.edu.url.tuproyecto.model.Usuario;
import gt.edu.url.tuproyecto.repository.UsuarioRepository;

@Component
public class CargadorUsuarios implements CommandLineRunner {

    private final UsuarioRepository usuarioRepository;
    private final PasswordEncoder passwordEncoder;
    private final String passwordAdmin;
    private final String passwordEntrenador;

    public CargadorUsuarios(UsuarioRepository usuarioRepository,
                            PasswordEncoder passwordEncoder,
                            @Value("${app.admin.password}") String passwordAdmin,
                            @Value("${app.entrenador.password}") String passwordEntrenador) {
        this.usuarioRepository = usuarioRepository;
        this.passwordEncoder = passwordEncoder;
        this.passwordAdmin = passwordAdmin;
        this.passwordEntrenador = passwordEntrenador;
    }

    @Override
    public void run(String... args) {
        crearSiNoExiste("admin", passwordAdmin, "ADMIN");
        crearSiNoExiste("entrenador", passwordEntrenador, "ENTRENADOR");
    }

    private void crearSiNoExiste(String username, String passwordPlano, String rol) {
        if (usuarioRepository.findByUsername(username).isEmpty()) {
            String hash = passwordEncoder.encode(passwordPlano);
            usuarioRepository.save(new Usuario(username, hash, rol));
        }
    }
}
Los nombres admin / entrenador y sus roles pueden adaptarse a tu institución (por ejemplo coordinador / voluntario), siempre iguales en las tres clases y en las plantillas. Las propiedades app.admin.password y app.entrenador.password deben coincidir con las de tu application.properties (Paso 5).
Trampa: cambiar la variable después no cambia la clave
El cargador solo crea. Si ya existe el usuario y cambias ADMIN_PASSWORD, la clave guardada sigue siendo la vieja. En desarrollo: detén la aplicación, borra la carpeta datos/ (se pierden tus registros de prueba; solo se hace en tu computadora) y arranca de nuevo.
✅ Checkpoint: la aplicación arranca sin errores con tus dos variables definidas y ya no aparece la línea "Using generated security password".

Paso 8 — Oculta lo que cada rol no debe ver Modifica tu lista

En tu plantilla de lista (la que muestra la tabla), modifica solo tres cosas; el resto de la plantilla queda como está.

(1) En la etiqueta <html>, agrega el espacio de nombres sec:

<html lang="es"
      xmlns:th="http://www.thymeleaf.org"
      xmlns:sec="http://www.thymeleaf.org/extras/spring-security">

(2) Arriba de la tabla, la barra con el nombre de quien tiene la sesión y el botón para cerrarla (cerrar sesión es un POST, por eso usa th:action):

<div class="barra">
  <span>Sesión de: <strong sec:authentication="name">usuario</strong></span>
  <form th:action="@{/logout}" method="post" class="en-linea">
    <button type="submit" class="secundario">Cerrar sesión</button>
  </form>
</div>

(3) Agrega sec:authorize="hasRole('ADMIN')" a cada elemento que solo el administrador debe ver: el enlace de crear, el encabezado de la columna de acciones y la celda con editar/eliminar:

<p sec:authorize="hasRole('ADMIN')"><a th:href="@{/RUTA/nuevo}">+ Agregar</a></p>

<th sec:authorize="hasRole('ADMIN')">Acciones</th>

<td sec:authorize="hasRole('ADMIN')">
  <a th:href="@{/RUTA/{id}/editar(id=${tuentidad.id})}">Editar</a>
  <form th:action="@{/RUTA/{id}/eliminar(id=${tuentidad.id})}" method="post" class="en-linea">
    <button type="submit" class="peligro">Eliminar</button>
  </form>
</td>

Revisa además que el formulario de crear/editar use th:action (no action), igual que en la Semana 12.

Ocultar un botón NO protege la ruta
sec:authorize es maquillaje: solo evita que el entrenador vea el botón. La protección real son las reglas requestMatchers de SecurityConfig. Compruébalo en el Paso 9: el entrenador que escribe a mano /RUTA/nuevo en la barra de direcciones debe recibir "Acceso denegado".
✅ Checkpoint: en tu lista aparece el nombre de quien tiene la sesión y el botón "Cerrar sesión".

Paso 9 — Prueba con los dos usuarios Comprueba lo nuevo

Con las variables definidas y la aplicación arrancada desde la terminal. Toma las capturas que pide el Entregable mientras pruebas:

  1. Sin sesión: abre http://localhost:8080/RUTA. Debe llevarte a /login. (captura 1: tu pantalla de login)
  2. Clave incorrecta: escribe una mala; debe volver al login con el mensaje de error.
  3. Como admin: entra con tu clave de administrador. Debes ver la lista, "Agregar" y las columnas de acciones. Crea, edita y elimina un registro. (captura 2: vista de administrador)
  4. Cerrar sesión: pulsa el botón; debe llevarte a /login con "Cerraste tu sesión."
  5. Como entrenador (tu segundo rol): entra con la otra clave. Debes ver la lista, sin "Agregar" ni acciones. (captura 3: vista del segundo rol)
  6. Intento prohibido: con esa misma sesión, escribe a mano http://localhost:8080/RUTA/nuevo. Debe salir "No tienes permiso para esta acción." (captura 4: el 403)
  7. Reinicio: detén la aplicación y vuelve a arrancarla con las variables. Tus registros siguen ahí y los usuarios siguen funcionando (el cargador no los crea otra vez).

Solución de problemas frecuentes
SituaciónQué hacer
Could not resolve placeholder 'ADMIN_PASSWORD' y la app no arrancaNo definiste la variable en esa terminal. Define las dos y arranca de nuevo con mvnw, no con el botón ▶.
Aparece Using generated security password y todo pide login con usuario userTienes Security pero no se carga tu configuración: revisa que SecurityConfig tenga @Configuration y esté dentro de tu paquete base.
Can't configure requestMatchers after anyRequestEscribiste anyRequest() antes de otras reglas. Va siempre al final.
Siempre dice "Usuario o contraseña incorrectos" y en consola Encoded password does not look like BCryptGuardaste la clave sin passwordEncoder.encode(...). Corrige el cargador, detén la app y borra datos/ (solo en desarrollo).
Cambié la variable pero la clave vieja sigue valiendoEl cargador solo crea usuarios nuevos. Detén la app, borra datos/ y arranca otra vez.
El entrenador sigue viendo los botones de administradorFalta la dependencia thymeleaf-extras-springsecurity6, el xmlns:sec en la etiqueta <html>, o el rol escrito en el sec:authorize no coincide con el guardado.
Al guardar o eliminar sale 403El formulario usa action= en lugar de th:action=, y no lleva el token CSRF. O es el entrenador intentando una acción de administrador (comportamiento correcto).
La página de login sale sin estiloTu archivo CSS no está en el permitAll() de SecurityConfig: ajusta la ruta.
Cerrar sesión da error 405 o 403El cierre de sesión es un POST con th:action="@{/logout}", no un enlace.
Database may be already in useHay otra copia de la aplicación abierta; ciérrala.
Mis datos desaparecen al reiniciarLa URL dice mem en lugar de file, o ddl-auto no es update.
