B. Los atributos de Thymeleaf

AtributoQué haceEjemplo
th:textReemplaza el contenido de la etiqueta con un dato<span th:text="${total}">0</span>
th:eachRepite la etiqueta una vez por cada elemento de una listath:each="j : ${jugadores}"

Los tres símbolos que hay que distinguir
${...} → una variable que mandó el controlador con model.addAttribute.
*{...} → un atributo dentro del objeto declarado en th:object (solo se usa en formularios).
@{...} → una dirección (URL). Úsalo siempre para enlaces y acciones de formulario.

Un formulario son siempre dos viajes, no uno
Es lo que más cuesta al inicio: no hay "una página de formulario", hay una ruta que lo muestra (GET) y otra que lo recibe (POST). Si tienes clara esa separación, todo lo demás encaja.

Los 6 pasos del circuito completo

Paso 1 — El usuario pide el formulario GET

Visita /jugadores/nuevo. El controlador prepara un objeto vacío y devuelve el nombre de la plantilla.

@GetMapping("/jugadores/nuevo")
public String mostrarFormulario(Model model) {
    model.addAttribute("jugador", new Jugador());   // ficha en blanco
    return "formulario";                            // templates/formulario.html
}

Paso 2 — Thymeleaf arma el HTML

El motor lee la plantilla, reemplaza los th: por HTML normal y lo envía al navegador. El usuario nunca ve un atributo th:.

<form th:action="@{/jugadores}" th:object="${jugador}" method="post">
    <input type="text" th:field="*{nombre}" />
</form>

<!-- lo que realmente le llega al navegador: -->
<form action="/jugadores" method="post">
    <input type="text" id="nombre" name="nombre" value="" />
</form>
th:field genera solo tres cosas: el id, el name y el value. Ese name="nombre" es la clave de todo lo que viene después.

Paso 3 — El usuario envía POST

Al pulsar "Guardar", el navegador manda los datos a la ruta del th:action, con el método post:

POST /jugadores
nombre=Ana&edad=12&posicion=Delantero
A diferencia del GET de la Semana 8, los datos no viajan en la barra de direcciones: van dentro de la petición. Por eso un POST no se puede probar escribiendo una URL en el navegador.

Paso 4 — Spring convierte los datos en un objeto (binding)

@PostMapping("/jugadores")
public String registrarJugador(@ModelAttribute Jugador jugador) { ... }

Spring hace exactamente esto, por dentro:

Jugador jugador = new Jugador();      // ← necesita el constructor vacío
jugador.setNombre("Ana");             // ← necesita los setters
jugador.setEdad(12);
jugador.setPosicion("Delantero");
Por eso el modelo necesita constructor vacío y setters
Si falta el constructor vacío, la aplicación falla al arrancar la petición. Si faltan los setters, el objeto llega vacío y sin ningún mensaje de error: se guarda un registro en blanco. Es el error más difícil de diagnosticar de la semana.

Paso 5 — El servicio guarda

jugadorService.guardar(jugador);   // lo agrega a la lista en memoria
El controlador no guarda: delega en el servicio, igual que en la Semana 9. Cada capa hace lo suyo.

Paso 6 — Redirigir, no mostrar

return "redirect:/jugadores";   // NO devuelve una plantilla
Por qué se redirige después de guardar
Si en vez de redirigir devolvieras "lista", la página se vería bien… pero la dirección del navegador seguiría siendo el POST. Al pulsar F5, el navegador vuelve a enviar el formulario y guarda el registro otra vez. Redirigiendo, el navegador hace un GET normal a /jugadores y recargar ya no duplica nada. Se le llama patrón POST → Redirect → GET, y el Challenge lo simula.
El circuito, en una frase
GET muestra la ficha en blanco → Thymeleaf la convierte en HTML → el usuario la envía → @ModelAttribute la vuelve un objeto Java → el servicio lo guarda → redirigimos para que recargar sea inofensivo.

Los errores marcados con 🔇 no muestran ningún mensaje: la aplicación funciona pero hace algo distinto de lo que esperabas. Son los que más tiempo hacen perder, así que revísalos primero cuando "todo parece bien".

Errores de plantillas y rutas

Mensaje o síntomaQué significaCómo se arregla
Error resolving template [formulario], template might not exist El nombre que devuelve el método no coincide con ningún archivo de templates/ Compara letra por letra. Se escribe sin .html y sin barra inicial: return "formulario";
🔇 El navegador muestra la palabra formulario como texto La clase quedó anotada con @RestController Cámbiala a @Controller y ajusta el import a org.springframework.stereotype.Controller.
🔇 La página se ve "en crudo", con los th: visibles o sin datos La plantilla quedó en static/ en vez de templates/ Muévela a src/main/resources/templates/.
Neither BindingResult nor plain target object for bean name 'jugador' available La plantilla usa th:object="${jugador}" pero el controlador no envió ese objeto Agrega model.addAttribute("jugador", new Jugador()); en el método GET. El nombre debe coincidir exactamente.
Error 405 Request method 'POST' not supported El formulario envía a una ruta que solo tiene @GetMapping Verifica que el th:action apunte a la ruta que tiene @PostMapping.
Error 400 al abrir /jugadores/abc El método espera un int en @PathVariable y llegó texto Es el comportamiento esperado. Solo enlaza números desde tu tabla.
El CSS no se aplica La ruta del <link> es incorrecta Usa th:href="@{/estilos.css}" y confirma que el archivo está en static/.

Ruta de diagnóstico en 30 segundos
1. ¿La página aparece? Si no → problema de plantilla o de @Controller. 2. ¿El formulario se envía? Si da 405 → la ruta del th:action. 3. ¿Llegan los datos? Imprime con System.out.println en el método POST. 4. ¿Llegan vacíos? → constructor vacío y setters del modelo.
