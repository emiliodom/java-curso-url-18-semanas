Semana 10 — Rutas, controladores y formularios

Sábado 19 de septiembre de 2026 · 11:10–12:20 · En línea · Dominio de la demo: Escuela de Fútbol Los Cerritos. Alcance: el registro se guarda en memoria; la base de datos es la Semana 12. Sin Entrega Parcial esta semana.

Objetivos (hoy)

  • Distinguir @Controller (devuelve una vista) de @RestController (devuelve datos).
  • Agregar la dependencia de Thymeleaf a un proyecto que ya existe.
  • Crear la primera plantilla en templates/ y entender por qué no va en static/.
  • Mostrar un formulario con th:object y th:field.
  • Recibir el envío con @PostMapping + @ModelAttribute y guardarlo en el servicio.
  • Aplicar el patrón guardar → redirigir → mostrar y explicar por qué existe.
  • Listar con th:each y abrir un detalle con @PathVariable.

Demostración que vale más que la explicación (1 minuto)
Deja a propósito @RestController en la clase nueva y visita la ruta: el navegador mostrará literalmente la palabra formulario. Cámbialo a @Controller delante de ellos y recarga: ahora aparece la página. Ese contraste fija la idea mejor que cualquier definición.

Agrega Thymeleaf al pom.xml, dentro de <dependencies>:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-thymeleaf</artifactId>
</dependency>

Al guardar, VS Code descarga la dependencia (la primera vez tarda). Recuerda la Semana 7: un Starter es un paquete de piezas ya combinadas; este trae el motor que convierte plantillas en HTML.

Carpeta nueva: src/main/resources/templates/. Explica la diferencia con static/:

CarpetaQué contiene¿Se puede abrir por URL directa?
static/Archivos que se entregan tal cual: CSS, imágenes, JSSí (/estilos.css)
templates/Plantillas que el servidor procesa antes de enviarlasNo. Solo se llega a ellas a través de un @Controller

Crea templates/formulario.html y el método que lo muestra:

@GetMapping("/jugadores/nuevo")
public String mostrarFormulario(Model model) {
    model.addAttribute("jugador", new Jugador());
    return "formulario";       // ← busca templates/formulario.html
}

Y en la plantilla, las tres piezas del enlace con el objeto:

<form th:action="@{/jugadores}" th:object="${jugador}" method="post">
    <input type="text" th:field="*{nombre}" />
    <input type="number" th:field="*{edad}" />
    <button type="submit">Guardar</button>
</form>
Las tres piezas, dichas despacio
th:object="${jugador}" = "este formulario llena ese objeto" · th:field="*{nombre}" = "esta casilla es ese atributo" (el * significa "dentro del objeto de arriba") · th:action="@{/jugadores}" = "envíalo a esta ruta". El @{...} construye la dirección correctamente aunque la aplicación cambie de carpeta.
Error que conviene provocar aquí
Escribe mal el nombre en el return (por ejemplo "formularios") y muestra el error resultante: Error resolving template [formularios], template might not exist. Es el error más frecuente de la semana y así lo reconocen cuando les pase solos.

  • Estirar, agua, mirar lejos de la pantalla 20 segundos.
  • Micro-check en el chat: "¿en qué carpeta va una plantilla de Thymeleaf?"

El método que recibe el envío:

@PostMapping("/jugadores")
public String registrarJugador(@ModelAttribute Jugador jugador) {
    jugadorService.guardar(jugador);
    return "redirect:/jugadores";
}
PiezaQué hace
@PostMapping("/jugadores")Atiende los envíos de formulario a esa ruta. Misma ruta que el @GetMapping de la lista, pero distinto método HTTP: no chocan.
@ModelAttribute Jugador jugadorSpring crea un Jugador y llena sus atributos con lo que venga del formulario, casando por nombre. Eso es el binding.
return "redirect:/jugadores";No devuelve una plantilla: le ordena al navegador que vaya a otra ruta.
Por qué el binding depende de los setters y del constructor vacío
Spring construye el objeto con el constructor sin parámetros y luego llama a setNombre(...), setEdad(...). Si la clase no tiene constructor vacío o le faltan los setters, el formulario "no guarda nada" sin decir por qué. Vale la pena abrir la clase Jugador y señalarlo.
Por qué se redirige en vez de devolver la plantilla (valor de la semana: experiencia de usuario)
Si después de guardar devolvieras directamente la lista, la dirección del navegador seguiría siendo el POST: al pulsar F5 el navegador vuelve a enviar el formulario y se guarda el registro otra vez. Redirigir cambia la dirección a un GET normal y recargar ya es inofensivo. El Challenge tiene un simulador que muestra exactamente ese duplicado.

El controlador pasa la lista a la plantilla, y Thymeleaf repite una fila por elemento:

<tr th:each="jugador, estado : ${jugadores}">
    <td th:text="${estado.count}">1</td>
    <td th:text="${jugador.nombre}">Nombre</td>
    <td th:text="${jugador.edad}">0</td>
</tr>

Y la ruta parametrizada para el detalle:

@GetMapping("/jugadores/{numero}")
public String verJugador(@PathVariable int numero, Model model) { ... }
Dos detalles que los estudiantes preguntan siempre
(1) El texto que escribes dentro de la etiqueta (>Nombre<) es solo relleno para poder abrir el archivo en el navegador mientras diseñas: al ejecutar, th:text lo reemplaza.
(2) /jugadores/nuevo y /jugadores/{numero} no chocan: Spring prefiere siempre la coincidencia literal antes que la variable.
Cierre honesto del alcance (importante decirlo aquí)
Reinicia el proyecto en vivo y muestra que la lista quedó vacía. "Los datos viven en memoria: se borran al apagar. En la Semana 12 conectamos una base de datos y esto ya no pasa." Anticiparlo evita que lo reporten como error durante la semana.

  2. Modela una vez el escenario "sin redirect" del simulador (2 min): se ve el registro duplicado al recargar.
