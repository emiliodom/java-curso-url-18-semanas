Ejercicios · Semana 10 · 100% en tu propia computadora

Del formulario al objeto Java, paso por paso

Dos pestañas: los 8 ejercicios en escalera y el Kit de archivos completos (cada archivo entero, con su ruta, su package y sus import). Proyecto de práctica: taller-formularios · Institución de ejemplo: Escuela de Fútbol Los Cerritos · Entidad: Jugador.
Cómo está armada esta escalera
Los ejercicios construyen un mismo módulo de registro, una pieza a la vez: primero mostrar una página, luego mostrar un formulario, luego recibirlo, luego guardarlo, luego listarlo. Al terminar los 8 tendrás exactamente el mismo circuito que pide la Guía 10, pero con un proyecto de práctica desechable.
Las tres preguntas ancla de esta semana
Cuando algo no funcione, revisa en este orden: (1) ¿el nombre que devuelve el método coincide con el nombre del archivo en templates/? (2) ¿el th:action del formulario apunta a la misma ruta que el @PostMapping? (3) ¿tu clase de modelo tiene constructor vacío y setters?

Ejercicio 1 — Agrega Thymeleaf Nivel 1

Abre el pom.xml de tu proyecto de práctica y agrega, dentro de <dependencies>, el bloque del Kit (archivo 2). Guarda y ejecuta el proyecto.

Tu turno: la primera ejecución tarda más de lo normal. ¿Por qué?

✅ Checkpoint: el proyecto arranca y muestra "Started ... Application" sin errores.
Solución
Porque Maven está descargando la dependencia nueva por primera vez (igual que en la Semana 7 con Spring Web). Se guarda en caché: las siguientes ejecuciones vuelven a ser rápidas. Si ves errores de descarga, revisa tu conexión y vuelve a ejecutar.

Ejercicio 2 — @Controller vs @RestController Nivel 1

Crea templates/saludo.html con un <h1> cualquiera. Luego crea una clase controladora con este método, pero anota la clase con @RestController (a propósito):

@GetMapping("/saludo")
public String saludo() {
    return "saludo";
}

Tu turno: visita /saludo. ¿Qué muestra? Ahora cambia a @Controller y recarga.

✅ Checkpoint: viste los dos comportamientos con el mismo método.
Solución
Con @RestController el navegador muestra literalmente la palabra saludo: la anotación devuelve el texto como contenido. Con @Controller, ese mismo texto se interpreta como el nombre de una plantilla, y Spring muestra templates/saludo.html. Es la distinción central de la semana.

Ejercicio 3 — Pasa datos a la plantilla Nivel 2

Agrega el método para enviar un dato. No debes borrar el código anterior. Muestralo en la plantilla:

// En el controlador
public String saludo(Model model) {
    model.addAttribute("institucion", "Escuela de Fútbol Los Cerritos");
    return "saludo";
}
<!-- En templates/saludo.html -->
<h1 th:text="${institucion}">Texto de relleno</h1>

Tu turno: ¿qué pasó con el texto "Texto de relleno"? ¿Para qué sirve entonces escribirlo?

Solución
Desapareció: th:text reemplaza el contenido de la etiqueta. Se escribe relleno para poder abrir el archivo directamente en el navegador mientras diseñas y ver cómo va quedando, sin tener que ejecutar el proyecto. No olvides el xmlns:th en la etiqueta <html> (ver Kit).

Ejercicio 4 — Muestra el formulario Nivel 2

Copia del Kit los archivos Jugador.java (archivo 4) y formulario.html (archivo 7), y crea el método que muestra el formulario:

@GetMapping("/jugadores/nuevo")
public String mostrarFormulario(Model model) {
    model.addAttribute("jugador", new Jugador());
    return "formulario";
}

Tu turno: ¿por qué hay que mandar un new Jugador() vacío si el usuario todavía no ha escrito nada?

✅ Checkpoint: /jugadores/nuevo muestra el formulario con sus tres campos.
Solución
Porque th:object="${jugador}" necesita un objeto al cual "amarrar" las casillas. Es como entregar una ficha en blanco: el formulario necesita saber qué va a llenar. Si no lo mandas, aparece el error Neither BindingResult nor plain target object for bean name 'jugador' available.

Ejercicio 5 — Recibe el envío Nivel 3

Agrega el método que atiende el POST. Por ahora, solo imprime en la terminal para comprobar que llegan los datos:

@PostMapping("/jugadores")
public String registrarJugador(@ModelAttribute Jugador jugador) {
    System.out.println("Llegó: " + jugador.getNombre() + ", " + jugador.getEdad());
    return "redirect:/jugadores/nuevo";
}

Tu turno: llena el formulario y envíalo. Mira la terminal de VS Code, no el navegador. ¿Qué aparece?

✅ Checkpoint: en la terminal aparece el nombre y la edad que escribiste.
Solución
Aparece Llegó: [lo que escribiste]. Eso demuestra el binding: Spring creó un objeto Jugador y llenó sus atributos con los datos del formulario, casándolos por nombre (th:field="*{nombre}" → setNombre(...)).
Si aparece null o 0: revisa que tu clase tenga los setters y el constructor vacío.

Ejercicio 6 — Guarda de verdad Nivel 3

Copia del Kit JugadorService.java (archivo 5), inyéctalo en el controlador por constructor (igual que en la Semana 9) y cambia el método del POST para que guarde y redirija a la lista.

Tu turno: registra dos jugadores. Luego detén y vuelve a ejecutar el proyecto y visita la lista. ¿Qué pasó?

✅ Checkpoint: al enviar el formulario, el navegador te lleva a /jugadores.
Solución
La lista quedó vacía: los datos vivían en una lista en memoria y se borraron al apagar la aplicación. No es un error tuyo — es el límite de esta semana. En la Semana 12 conectarás una base de datos y los datos sobrevivirán a los reinicios.

Ejercicio 7 — Lista con th:each Nivel 3

Copia del Kit lista.html (archivo 8) y agrega el método @GetMapping("/jugadores") que manda la lista al modelo.

Tu turno: registra tres jugadores y observa la tabla. Ahora fíjate en el @GetMapping("/jugadores") y el @PostMapping("/jugadores"): ¿por qué no chocan si tienen la misma ruta?

✅ Checkpoint: la tabla muestra una fila por jugador registrado, numeradas.
Solución
Porque una ruta se identifica por dirección + método HTTP. GET /jugadores ("muéstrame la lista") y POST /jugadores ("guarda este nuevo") son dos rutas distintas aunque compartan la dirección. Es una convención muy común en aplicaciones web.

Ejercicio 8 — Reto: detalle con ruta parametrizada Nivel 4

Copia del Kit detalle.html (archivo 9) y escribe tú el método @GetMapping("/jugadores/{numero}") con @PathVariable, usando buscarPorNumero() del servicio. Enlázalo desde la tabla.

Tu turno: prueba tres direcciones: /jugadores/1, /jugadores/99 y /jugadores/abc. ¿Qué pasa en cada una y por qué?

✅ Checkpoint: /jugadores/1 muestra el primer jugador registrado.
Solución
/jugadores/1 muestra el detalle. /jugadores/99 no encuentra a nadie: el servicio devuelve null y el controlador redirige a la lista (por eso conviene esa comprobación). /jugadores/abc da un error 400, porque el método espera un int y "abc" no se puede convertir a número.
Bonus: /jugadores/nuevo sigue funcionando aunque parezca que choca con {numero}, porque Spring prefiere siempre la coincidencia literal antes que la variable.

4. Jugador.java — el modelo lo creas tú

Ruta: src/main/java/gt/edu/url/tallerformularios/model/Jugador.java

package gt.edu.url.tallerformularios.model;

public class Jugador {

    private String nombre;
    private int edad;
    private String posicion;

    // Constructor vacío: OBLIGATORIO para que el formulario funcione.
    public Jugador() {
    }

    public Jugador(String nombre, int edad, String posicion) {
        this.nombre = nombre;
        this.edad = edad;
        this.posicion = posicion;
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }

    public int getEdad() {
        return edad;
    }

    public void setEdad(int edad) {
        this.edad = edad;
    }

    public String getPosicion() {
        return posicion;
    }

    public void setPosicion(String posicion) {
        this.posicion = posicion;
    }
}
Las dos cosas sin las cuales el formulario "no guarda nada"
(1) El constructor vacío: Spring crea el objeto llamándolo antes de llenarlo. Ojo: si escribes un constructor con parámetros, Java ya no te da el vacío gratis — hay que escribirlo, como arriba.
(2) Los setters: Spring llena cada campo llamando a setNombre(...), setEdad(...). Sin ellos el objeto llega vacío y no aparece ningún error, solo datos en blanco. Los getters son igual de necesarios para que Thymeleaf pueda mostrar los valores.

5. JugadorService.java lo creas tú

Ruta: src/main/java/gt/edu/url/tallerformularios/service/JugadorService.java

package gt.edu.url.tallerformularios.service;

import java.util.ArrayList;
import java.util.List;

import org.springframework.stereotype.Service;

import gt.edu.url.tallerformularios.model.Jugador;

@Service
public class JugadorService {

    // La "memoria" de la aplicación: se vacía cada vez que reinicias.
    private final List<Jugador> jugadores = new ArrayList<>();

    public void guardar(Jugador jugador) {
        jugadores.add(jugador);
    }

    public List<Jugador> listarTodos() {
        return jugadores;
    }

    public int contar() {
        return jugadores.size();
    }

    public Jugador buscarPorNumero(int numero) {
        if (numero < 1 || numero > jugadores.size()) {
            return null;
        }
        return jugadores.get(numero - 1);
    }
}
ImportPara qué sirve
java.util.ListEl tipo "lista" (una colección ordenada de objetos)
java.util.ArrayListLa implementación concreta que se usa al crearla con new
org.springframework.stereotype.ServiceHabilita @Service
…model.JugadorTu propia clase, que vive en otro paquete

6. JugadorController.java lo creas tú

Ruta: src/main/java/gt/edu/url/tallerformularios/controller/JugadorController.java

package gt.edu.url.tallerformularios.controller;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;

import gt.edu.url.tallerformularios.model.Jugador;
import gt.edu.url.tallerformularios.service.JugadorService;

@Controller
public class JugadorController {

    private final JugadorService jugadorService;

    public JugadorController(JugadorService jugadorService) {
        this.jugadorService = jugadorService;
    }

    // 1. Muestra el formulario vacío
    @GetMapping("/jugadores/nuevo")
    public String mostrarFormulario(Model model) {
        model.addAttribute("jugador", new Jugador());
        return "formulario";
    }

    // 2. Recibe el formulario, guarda y redirige
    @PostMapping("/jugadores")
    public String registrarJugador(@ModelAttribute Jugador jugador) {
        jugadorService.guardar(jugador);
        return "redirect:/jugadores";
    }

    // 3. Muestra la lista
    @GetMapping("/jugadores")
    public String listarJugadores(Model model) {
        model.addAttribute("jugadores", jugadorService.listarTodos());
        model.addAttribute("total", jugadorService.contar());
        return "lista";
    }

    // 4. Muestra el detalle de uno solo (ruta parametrizada)
    @GetMapping("/jugadores/{numero}")
    public String verJugador(@PathVariable int numero, Model model) {
        Jugador jugador = jugadorService.buscarPorNumero(numero);
        if (jugador == null) {
            return "redirect:/jugadores";
        }
        model.addAttribute("jugador", jugador);
        model.addAttribute("numero", numero);
        return "detalle";
    }
}
ImportPara qué sirveSi falta…
…stereotype.ControllerHabilita @Controller (¡no es el mismo paquete que @RestController!)cannot find symbol: Controller
org.springframework.ui.ModelEl "maletín" donde metes los datos que la plantilla va a mostrarcannot find symbol: Model
…annotation.GetMappingRutas que se visitan (mostrar)cannot find symbol: GetMapping
…annotation.PostMappingRutas que reciben formularios (guardar)cannot find symbol: PostMapping
…annotation.ModelAttributeConvierte los campos del formulario en un objeto Javacannot find symbol: ModelAttribute
…annotation.PathVariableLee un valor incrustado en la ruta (/jugadores/3)cannot find symbol: PathVariable
…model.Jugador y …service.JugadorServiceTus propias clases, en otros paquetescannot find symbol

El xmlns:th no es decoración
Esa línea en la etiqueta <html> es la que le dice al editor y a Thymeleaf que los atributos th: son válidos. Si la omites, el proyecto puede funcionar, pero VS Code te marcará advertencias en todo el archivo y perderás el autocompletado.

    <thead>
      <tr>
        <th>#</th><th>Nombre</th><th>Edad</th><th>Posición</th><th></th>
      </tr>
    </thead>
    <tbody>
      <tr th:each="jugador, estado : ${jugadores}">
        <td th:text="${estado.count}">1</td>
        <td th:text="${jugador.nombre}">Nombre de ejemplo</td>
        <td th:text="${jugador.edad}">0</td>
        <td th:text="${jugador.posicion}">Posición</td>
        <td><a th:href="@{/jugadores/{n}(n=${estado.count})}">Ver</a></td>
      </tr>
    </tbody>
  </table>

  <p><a th:href="@{/jugadores/nuevo}">Registrar otro jugador</a></p>
</main>
</body>
</html>
AtributoQué hace
th:each="jugador, estado : ${jugadores}"Repite esa fila una vez por cada elemento. jugador es el elemento actual; estado trae información extra del recorrido.
${estado.count}El número de la vuelta actual, empezando en 1 (útil para numerar).
th:if="${total == 0}"Muestra la etiqueta solo si la condición se cumple.
@{/jugadores/{n}(n=${estado.count})}Construye una dirección con un valor variable: /jugadores/1, /jugadores/2…
