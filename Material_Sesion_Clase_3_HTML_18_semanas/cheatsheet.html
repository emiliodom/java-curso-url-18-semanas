Cheat Sheet · Semana 3 · GitHub Desktop

Referencia rápida — botones, no comandos

De cero a tu primera Pull Request, todo a punta de clics. Guárdala: la usarás toda la semana. ¿Prefieres o necesitas la terminal? Mira el Anexo: Comandos.
Las 3 zonas de Git (repaso rápido)
1. Directorio de trabajo (tus archivos tal cual, en el Explorador de VS Code) → 2. Área de preparación / staging (la casilla marcada junto a cada archivo en la pestaña "Changes" de GitHub Desktop) → 3. Repositorio (botón "Commit to main": historial guardado permanentemente).

A. Tu primer commit — paso a paso

  1. Abre GitHub Desktop y confirma que estás dentro del repositorio correcto (nombre arriba a la izquierda, botón "Current Repository").
  2. Edita tus archivos donde quieras: en el Explorador de VS Code (Repository → Open in Visual Studio Code) o desde cualquier programa. Guarda con Ctrl + S.
  3. Vuelve a GitHub Desktop → pestaña "Changes" (columna izquierda): tus archivos editados aparecen listados, con el cambio resaltado en la vista previa.
  4. Confirma que la casilla junto a cada archivo esté marcada (equivalente a git add: lo deja "preparado" para el commit).
  5. Abajo a la izquierda, escribe un mensaje breve y claro en "Summary", en presente: por ejemplo "Agrega estructura inicial del proyecto".
  6. Clic en el botón azul "Commit to main".
Antes de tu primer commit en una computadora nueva, GitHub Desktop te pide tu nombre y correo en la pantalla "Configure Git" (paso único, ver Instala GitHub Desktop — Paso 5).

B. Publicar tu proyecto en GitHub

  1. Con al menos un commit hecho (sección A), busca el botón "Publish repository" arriba de la ventana.
  2. En la ventana que se abre: confirma el nombre y decide si será público (recomendado para este curso, así tu profesor puede verlo) — desmarca "Keep this code private" si quieres que sea público.
  3. Clic en "Publish Repository". Este único botón hace, por debajo, lo mismo que conectar un remoto y subir el historial por primera vez.
  4. Para confirmar: menú Repository → View on GitHub — se abre tu navegador mostrando el repositorio ya en línea.
  5. Para cambios futuros: edita → "Changes" → Summary → "Commit to main" → botón "Push origin" (reemplaza a "Publish repository", que solo se usa la primera vez).

C. Crear una branch (rama)

Una rama es una copia paralela del proyecto donde puedes experimentar sin afectar main (la rama principal, siempre estable).

  1. Arriba, clic en el botón "Current Branch" (muestra el nombre de tu rama actual).
  2. Clic en "New Branch", escribe un nombre descriptivo (ej. feature-formulario) → "Create Branch". GitHub Desktop te mueve a esa rama automáticamente.
  3. Trabaja normalmente en esa rama: edita archivos, luego "Changes" → Summary → "Commit to main" (el botón mostrará el nombre de tu rama, no literalmente "main").
  4. Sube la rama nueva a GitHub con el botón "Publish branch" (aparece porque es una rama nueva que aún no existe en GitHub).
  5. Para volver a main en cualquier momento: botón "Current Branch" → selecciona main de la lista.

D. Crear una Pull Request (PR)

Una Pull Request es una propuesta formal de integrar los cambios de tu rama a otra (normalmente main), con espacio para que alguien más los revise antes. Este paso se hace en github.com, sin importar si trabajaste con GitHub Desktop o con comandos.

  1. Con tu rama ya subida (paso C.4), en GitHub Desktop puedes usar el menú Branch → Create Pull Request (abre tu navegador directo en la página correcta).
  2. GitHub suele mostrar un botón "Compare & pull request" apenas subes una rama nueva.
  3. Verifica la dirección de la comparación: base: main ← compare: nombre-de-tu-rama (tus cambios van HACIA main, no al revés).
  4. Escribe un título claro y, en la descripción, qué cambia y por qué.
  5. Clic en "Create pull request". En equipo, un compañero revisa el código y comenta o aprueba antes del siguiente paso.

E. Merge a una branch diferente

Merge ("fusionar") integra los cambios de una rama dentro de otra.

  1. Abre la Pull Request ya creada (paso D). Si no hay conflictos, aparece el botón "Merge pull request" en github.com.
  2. Clic en "Merge pull request" → "Confirm merge". Los cambios ya quedan integrados en main (en GitHub).
  3. En GitHub Desktop: botón "Current Branch" → selecciona main → clic en "Fetch origin" (trae los cambios recién fusionados a tu computadora).
  4. (Opcional) borra la rama que ya cumplió su propósito: clic derecho sobre ella en "Current Branch" → "Delete".
Nota: el flujo de ramas, Pull Requests y merge se profundiza en la Semana 4 (incluyendo cómo resolver conflictos). Esta sección es tu referencia de adelanto.

G. .gitignore (plantilla para el proyecto del curso)

Al crear el repositorio con File → New Repository…, el desplegable "Git ignore" te deja elegir "Java" — GitHub Desktop genera el archivo por ti, automáticamente. Si quieres agregarle líneas extra, ábrelo desde VS Code y complétalo así:

# Java / Maven (lo usarás desde la Semana 7)
target/
*.class
.idea/
*.iml

# General
.DS_Store
*.log
notas_personales.txt
Es un archivo de texto plano llamado exactamente .gitignore (con el punto al inicio), en la raíz del proyecto. Los archivos que coincidan con esas líneas dejan de aparecer en "Changes".

H. Problemas comunes y su traducción

GitHub Desktop muestra…Significa…
Botón "Commit to main" gris/deshabilitadoFalta escribir el mensaje en "Summary", o no hay ningún archivo marcado en "Changes".
No aparece "Publish repository"Ese botón solo aparece la primera vez; después se llama "Push origin". Revisa que tengas sesión iniciada.
"This branch is X commits behind main"Alguien (o tú, en otra computadora) subió cambios que aún no tienes; clic en "Fetch origin" para traerlos.
Repositorio publicado como privadoEn github.com → Settings → Danger Zone → "Change repository visibility" → Public.
"There isn't anything to commit"No hay cambios nuevos que guardar — todo ya está en el último commit.
