Los mismos pasos, ahora con comandos

Esta semana practicaste con GitHub Desktop: botones, ventanas, clics. Todo lo que hiciste ahí lo puedes hacer también escribiéndolo en una terminal — es exactamente el mismo Git por debajo. Este anexo es tu referencia para cuando quieras (o necesites, por ejemplo trabajando en equipo) usar comandos directamente.
¿Por qué aprender esto si ya me funciona con clics?
Tres razones prácticas: los comandos son más rápidos una vez que los memorizas, funcionan en cualquier servidor sin interfaz gráfica (donde se despliegan la mayoría de aplicaciones reales), y son el estándar de la industria — todo tutorial, foro o compañero de trabajo asume que los conoces. No hay prisa: domina primero GitHub Desktop, y vuelve aquí cuando te sientas lista para el siguiente nivel.
Traducción rápida: lo que ya sabes hacer con clics ↔ el comando equivalente

A. Tu primer commit — paso a paso

  1. Ubícate en la carpeta de tu proyecto: 
    cd ruta/a/tu/proyecto
  2. Inicializa Git (una sola vez por proyecto): 
    git init
  3. Revisa qué ve Git (archivos nuevos aparecen en rojo = "untracked"): 
    git status
  4. Agrega los archivos al área de preparación: 
    git add nombre-del-archivo
# o todos los archivos a la vez:
git add .
  5. Vuelve a revisar (ahora en verde = listos para el commit): 
    git status
  6. Crea el commit con un mensaje claro, en presente: 
    git commit -m "Agrega estructura inicial del proyecto"
  7. Confirma que quedó guardado en el historial: 
    git log --oneline
Antes de tu primer commit en cualquier computadora nueva, Git necesita saber quién eres: git config --global user.name "Tu Nombre" y git config --global user.email "tu@correo.com" (una sola vez, ver Semana 1).

B. Push origin — subir tu proyecto a GitHub

  1. Crea un repositorio vacío en github.com/new (botón "New repository"). No marques "Add a README" si ya tienes archivos locales.
  2. Copia la URL HTTPS que te muestra GitHub, por ejemplo: 
    https://github.com/tu-usuario/tu-repo.git
  3. Conecta tu repositorio local con ese remoto (origin es solo un apodo para esa dirección): 
    git remote add origin https://github.com/tu-usuario/tu-repo.git
  4. Verifica que quedó conectado: 
    git remote -v
  5. Asegúrate de que tu rama principal se llame main (el estándar actual de GitHub): 
    git branch -M main
  6. Sube tus commits por primera vez: 
    git push -u origin main
    El -u ("upstream") solo se necesita la primera vez: conecta tu rama local con la remota. Después, para subir cambios nuevos basta con git push.
  7. Refresca GitHub.com en el navegador: tus archivos deben aparecer ahí.

C. Crear una branch (rama)

Una rama es una copia paralela del proyecto donde puedes experimentar sin afectar main (la rama principal, siempre estable).

  1. Revisa en qué rama estás ahora mismo (la actual tiene un *): 
    git branch
  2. Crea una rama nueva y muévete a ella en un solo paso: 
    git checkout -b nombre-de-tu-rama
# forma moderna equivalente:
git switch -c nombre-de-tu-rama
  3. Trabaja normalmente en esa rama: edita archivos, luego git add y git commit (igual que en la sección A).
  4. Sube la rama nueva a GitHub (la primera vez necesita -u, igual que con main): 
    git push -u origin nombre-de-tu-rama
  5. Para volver a main en cualquier momento: 
    git checkout main
# o: git switch main

D. Crear una Pull Request (PR)

Una Pull Request es una propuesta formal de integrar los cambios de tu rama a otra (normalmente main), con espacio para que alguien más los revise antes. Este paso siempre se hace en github.com, sin importar si el resto lo hiciste con comandos o con GitHub Desktop.

  1. Con tu rama ya subida a GitHub (paso C.4), entra a la página del repositorio en github.com.
  2. GitHub suele mostrar un botón "Compare & pull request" apenas subes una rama nueva — haz clic ahí. Si no aparece: pestaña "Pull requests" → "New pull request".
  3. Verifica la dirección de la comparación: base: main ← compare: nombre-de-tu-rama (tus cambios van HACIA main, no al revés).
  4. Escribe un título claro y, en la descripción, qué cambia y por qué.
  5. Clic en "Create pull request". En equipo, un compañero revisa el código y comenta o aprueba antes del siguiente paso.

E. Merge a una branch diferente

Merge ("fusionar") integra los cambios de una rama dentro de otra. Puede hacerse desde GitHub (con una PR) o directo en la terminal.

Opción 1 — Desde la Pull Request (recomendado en equipo)

  1. Abre la Pull Request ya creada (paso D). Si no hay conflictos, aparece el botón "Merge pull request".
  2. Clic en "Merge pull request" → "Confirm merge". Los cambios de tu rama ya quedan integrados en main (en GitHub).
  3. En tu computadora, vuelve a main y trae esos cambios: 
    git checkout main
git pull origin main
  4. (Opcional) borra la rama que ya cumplió su propósito: 
    git branch -d nombre-de-tu-rama            # borra la rama local
git push origin --delete nombre-de-tu-rama # borra la rama remota

Opción 2 — Directo en la terminal (sin PR, para practicar el concepto)

git checkout main
git merge nombre-de-tu-rama
Fusiona los cambios de nombre-de-tu-rama dentro de main, sin pasar por GitHub. Útil para entender qué hace un merge, aunque en equipo se prefiere siempre la Opción 1 (con revisión).
Nota: el flujo de ramas, Pull Requests y merge se profundiza en la Semana 4 (incluyendo cómo resolver conflictos). Esta sección es tu referencia de adelanto.

G. .gitignore (plantilla para el proyecto del curso)

# Java / Maven (lo usarás desde la Semana 7)
target/
*.class
.idea/
*.iml

# General
.DS_Store
*.log
notas_personales.txt
Archivo de texto plano llamado exactamente .gitignore (con el punto al inicio), en la raíz del proyecto. Git deja de "ver" lo que coincida con esas líneas. Si creaste tu repositorio con GitHub Desktop y elegiste "Git ignore: Java" al crearlo, esta plantilla ya viene incluida — puedes agregarle estas líneas extra.

H. Errores comunes y su traducción

Git dice…Significa…
fatal: not a git repositoryNo has corrido git init aquí, o estás en la carpeta equivocada.
Please tell me who you areFalta configurar user.name/user.email (sección A, nota).
nothing to commit, working tree cleanNo hay cambios nuevos que guardar — todo ya está en el último commit.
fatal: remote origin already existsYa conectaste un remoto antes; usa git remote set-url origin NUEVA_URL para cambiarlo.
failed to push some refs (rejected)El remoto tiene cambios que tú no tienes localmente; haz git pull antes de volver a intentar git push.
CONFLICT (content)Dos cambios chocan en la misma línea; hay que editar el archivo a mano y decidir qué queda (se profundiza en la Semana 4).
