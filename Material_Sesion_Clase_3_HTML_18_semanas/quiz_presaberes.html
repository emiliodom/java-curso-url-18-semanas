Quiz de Presaberes · 5 minutos · No cuenta para nota

¿De dónde partimos hoy?

8 preguntas sobre respaldos, versiones e intuición de "guardar cambios". Responde honestamente: es tu foto de entrada.
1) Guardaste 3 versiones de un trabajo: ensayo.docx, ensayo_v2.docx, ensayo_final_FINAL.docx. ¿Qué problema tiene esta forma de "versionar"?
✅ Exacto: sin un historial real, los nombres de archivo no explican qué cambió ni por qué. Eso resuelve el control de versiones.
El problema real es que esos nombres no dicen qué cambió, quién y cuándo. Hoy verás cómo Git resuelve esto con un historial ordenado.
2) Google Docs guarda automáticamente un "historial de versiones" que puedes revisar. ¿A qué se parece más esa idea en programación?
✅ Correcto: es exactamente la misma idea, aplicada a código en vez de documentos de texto.
Se parece a un sistema de control de versiones: un historial de "fotografías" con autor y fecha. Hoy conocerás Git, la herramienta que hace justo eso para el código.
3) Si guardas tu proyecto SOLO en tu computadora y esta se daña, ¿qué pasa con tu trabajo?
✅ Correcto. Por eso hoy aprenderás a tener una copia remota en GitHub: tu red de seguridad.
Se pierde. Por eso hoy subirás tu proyecto a GitHub: una copia en internet que sobrevive aunque tu computadora falle.
4) ¿Cuál de estos mensajes describe mejor "qué cambió" en un commit?
✅ Correcto: un buen mensaje dice qué cambia y, si hace falta, por qué. Es el estándar profesional que verás hoy.
La opción B: describe con claridad qué cambió. "cambios" o "asdasd" no le sirven a nadie, ni siquiera a ti mismo en un mes.
5) Dos personas trabajan en el mismo proyecto a la vez. Sin ninguna herramienta de control de versiones, ¿qué es más probable que pase?
✅ Correcto: sin control de versiones, es fácil perder el trabajo de alguien sin darte cuenta.
Es muy probable que uno sobrescriba el trabajo del otro. Git (y GitHub) existen justo para evitar esto de forma ordenada.
6) "GitHub" y "Git" suenan parecido. ¿Cuál es la diferencia?
✅ Exacto. Hoy usarás ambos: Git en tu terminal, GitHub en el navegador.
Git es la herramienta local; GitHub es el sitio remoto donde subes ese historial para respaldarlo y compartirlo.
7) ¿Has usado GitHub antes, aunque sea para descargar el código de otra persona?
✅ Cualquier respuesta es válida aquí — es solo diagnóstica. Hoy lo usarás de forma activa, no solo para mirar código ajeno.
Cualquier respuesta era válida 🙂 — hoy, sin importar tu experiencia previa, crearás y subirás tu propio repositorio.
8) Escribiste mal un comando en la terminal y aparece un mensaje en inglés que no entiendes. ¿Qué haces primero?
✅ Esa es la actitud que ya practicamos desde la Semana 1: los mensajes de error (también en Git) son información, no un castigo.
Lo mejor es leer el mensaje: Git suele decir exactamente qué falta (ver la tabla de errores en el cheat sheet de hoy).
