Semana 3 — Git y GitHub: control de versiones

Sábado 25 de julio de 2026 · 11:10–12:20 · En línea · Requiere GitHub Desktop instalado (o Git, ver Semana 1) y cuenta de GitHub.
Abrir GitHub

Objetivos (hoy)

  • Explicar qué es el control de versiones y por qué importa.
  • Verificar/instalar Git y configurarlo con nombre y correo.
  • Ejecutar el flujo local: init → add → commit → log.
  • Conectar un repositorio local con GitHub y hacer push.
  • Escribir mensajes de commit claros (buena práctica desde hoy).

Normas rápidas

  • Un commit = una idea/cambio completo, no "guardado automático".
  • Mensaje de commit en presente/imperativo: "Agrega README", no "agregué" ni "cambios".
  • git status es tu mejor amigo: úsalo antes de cada paso si dudas.
  • Nunca subas contraseñas ni archivos pesados al repositorio (usa .gitignore).
Checklist antes de iniciar (docente)
  • Confirmar quiénes tienen GitHub Desktop instalado (o Git por comandos) y quiénes no.
  • Tener una cuenta de GitHub propia lista para la demo en pantalla.
  • Crear (o limpiar) una carpeta de práctica de ejemplo antes de clase.
  • Plan B listo por si GitHub.com está lento/caído (ver más abajo).

Guion minuto a minuto (70 min)

  1. Saluda y conecta con la Semana 2: "ya escribes programas completos; hoy aprendes a no perderlos nunca".
  2. Comparte el enlace del Quiz de Presaberes (4 minutos, individual).
  3. Pregunta rápida: "¿Alguna vez perdiste un archivo importante, o guardaste versiones como trabajo_final_v2_YA.docx?"

Pregunta detonadora: "¿Qué pasa si dos personas editan el mismo documento de Word a la vez?" → puente a: control de versiones = un historial ordenado de "fotografías" del proyecto, con autor y momento exacto de cada cambio.

  • Git: el programa que toma esas fotografías (commits) en tu computadora.
  • GitHub: un lugar en internet donde guardas una copia de ese historial y colaboras con otros.
  • Analogía: Git es como el historial de versiones de Google Docs, pero tú decides cuándo tomar cada fotografía y qué incluir en ella.

Verificación rápida (todos en su terminal):

git --version
git config --global --list
Si falta Git o no aparece nombre/correo
Recordar los pasos de instalacion.html — Paso 4 (Semana 1). Sin nombre/correo configurados, Git rechazará el primer commit con "Please tell me who you are".

Demostración en vivo, paso a paso, en una carpeta nueva:

mkdir mi-primer-repo
cd mi-primer-repo

git init                          # crea el repositorio (una vez por proyecto)
git status                        # ¿qué ve Git? (nada todavía)

echo "Mi primer proyecto" > README.md
git status                        # README.md aparece en rojo: "untracked"

git add README.md                 # lo pasa al área de preparación (staging)
git status                        # ahora aparece en verde: listo para commit

git commit -m "Agrega README inicial"
git log --oneline                 # historial: aparece tu commit
  • Las 3 zonas de Git: directorio de trabajo (tus archivos) → área de preparación/staging (git add) → repositorio (git commit).
  • git status se usa constantemente: dice en qué zona está cada archivo.
  • Un commit sin -m "mensaje" abre un editor de texto (a veces Vim) — recordar configurar VS Code como editor de Git (visto en instalación, Semana 1).
Orden y trazabilidad (valor de la semana)
Un buen mensaje de commit responde "¿qué cambia y por qué?" en pocas palabras, en presente: "Agrega validación de edad", no "cambios" ni "asdasd".

Demostración en pantalla: crear un repositorio vacío en github.com/new (sin marcar "Add a README" porque ya tenemos uno local) y conectar:

git remote add origin https://github.com/tu-usuario/mi-primer-repo.git
git remote -v                     # confirma la conexión

git branch -M main                # asegura que la rama se llame "main"
git push -u origin main           # sube el historial completo por primera vez
  • remote = la dirección de un repositorio en internet. origin es solo un apodo (el más común) para esa dirección.
  • -u en el primer push "recuerda" la conexión: después basta con git push.
  • Refrescar GitHub en el navegador y mostrar que los archivos ya aparecen ahí — "tu código ya no vive solo en tu computadora".
Error común: "failed to push some refs (rejected)"
Pasa cuando el repositorio remoto tiene algo que tu copia local no tiene (ej. sí marcaste "Add a README" en GitHub). Solución: git pull origin main --allow-unrelated-histories y luego git push. Se profundiza en la Semana 4.
Adelanto: ramas, Pull Request y merge
Hoy trabajamos directo sobre main. La próxima semana (Ramas y colaboración) veremos cómo crear una rama para cada cambio y proponerlo con una Pull Request. El cheat sheet de hoy ya incluye la referencia rápida de esos comandos por si quieres adelantarte.

  • Estirar manos y espalda, agua, mirar lejos de la pantalla 20 segundos.
  • Micro-check en el chat: "¿ya ves tus archivos en GitHub.com?"

Comparar mensajes de commit reales (buenos vs. malos) y explicar .gitignore: un archivo de texto que le dice a Git qué NO debe vigilar.

# .gitignore para un proyecto Java
target/
*.class
.idea/
*.iml
.DS_Store
  • ¿Por qué no subir carpetas generadas (target/) o archivos del sistema operativo? Ocupan espacio y generan conflictos innecesarios.
  • Regla de oro: nunca subir contraseñas, llaves de API ni datos sensibles — ni siquiera en un repositorio "privado".
Seguridad colaborativa (valor de la semana)
El control de versiones no es solo para colaborar: es tu red de seguridad personal. Si algo se rompe, siempre puedes volver a un commit anterior que funcionaba.

  1. Comparte el enlace del Challenge — Ordena el flujo Git.
  2. Modela el nivel Fácil en pantalla (1 min): ordenar los comandos de un primer commit local.
  3. Los estudiantes resuelven Medio (conectar con GitHub) y, si alcanza, Difícil (rama + push) — 7 min. El juego da retroalimentación instantánea (toasts) en cada movimiento.
  4. Quien termine antes: continúa con los Ejercicios 5–8 en su propia GitHub Desktop.
Preguntas guía (docente, mientras circula por salas)
¿Por qué ese comando va antes? ¿Qué pasaría si haces push antes de commit? ¿Qué zona de Git modifica cada comando?

  1. Comparte el enlace del Quiz de Final de Clase (10 preguntas, individual, 7 min).
  2. Al terminar, cada estudiante pulsa Calificar, revisa la retroalimentación y exporta su resultado a PDF.
  3. Los PDF del quiz y del challenge = evidencia de la Actividad en clase – Sesión 3.

  • Síntesis en 3 frases: fotografiar cambios (commit), guardarlos en internet (push), nunca perder el progreso.
  • Ticket de salida en el chat: 1 aprendizaje + 1 duda.
  • Invitación a la evaluación anónima de la sesión.
  • Presenta el Entregable — Guía de Aprendizaje 3: crear el repositorio inicial del proyecto del curso en GitHub, fecha límite antes de la Sesión 4 (1 de agosto de 2026).
  • Puente a la semana 4: "hoy trabajaste solo en main; la próxima semana usarás ramas para trabajar sin romper lo que ya funciona, y propondrás cambios con una Pull Request".
Plan B (si la tecnología falla)
Si alguien se traba con la terminal (o no tiene Git instalado): cambiar a GitHub Desktop — mismo resultado, 100% a punta de clics, sin comandos que memorizar. Si ni siquiera eso se puede instalar hoy: Learn Git Branching (simulador de Git en el navegador) para practicar mientras se pone al día con la instalación durante la semana, o crear/editar archivos directo en la interfaz web de GitHub (botón "Add file") como alternativa temporal a git push.
