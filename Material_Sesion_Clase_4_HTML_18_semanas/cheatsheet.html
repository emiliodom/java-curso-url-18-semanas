Referencia rápida — ramas, Pull Requests y README

Guárdala: la usarás toda la semana, en tu repositorio de práctica y en tu proyecto real.
Regla de oro de la semana
main siempre debe funcionar. Cualquier cambio nuevo — por pequeño que sea — empieza en una rama, y solo vuelve a main a través de una Pull Request revisada.

A. Crear una rama y trabajar en ella

  1. Botón "Current Branch" (arriba) → "New Branch".
  2. Nombre descriptivo y en minúsculas, con guiones: feature-nombre-corto (ej. feature-login), nunca prueba o cosas.
  3. Clic en "Create Branch" — te mueve automáticamente a ella.
  4. Edita tus archivos con normalidad; "Changes" → Summary → "Commit to nombre-de-tu-rama" (fíjate que el botón ya no dice "main").

B. Publicar la rama y crear una Pull Request

  1. Con al menos un commit en tu rama: clic en "Publish branch".
  2. Menú Branch → Create Pull Request (o el botón "Compare & pull request" en github.com).
  3. Verifica la dirección: base: main ← compare: tu-rama — tus cambios van HACIA main.
  4. Título claro + descripción de qué cambia y por qué → "Create pull request".

C. Revisar código con respeto

En la pestaña "Files changed" de la Pull Request, cualquiera con acceso puede comentar una línea específica (ícono "+" a la izquierda de la línea).

Comentario destructivo (evitar)Comentario constructivo (usar)
"Esto está mal.""¿Consideraste validar que el campo no esté vacío antes de guardarlo?"
"No entiendo por qué hiciste esto.""¿Podrías agregar un comentario explicando por qué se necesita este cálculo?"
(sin comentar nada, solo rechazar)Aprobar con una sugerencia concreta de mejora para después.

D. Aprobar y fusionar (merge)

  1. Sin conflictos pendientes, la Pull Request muestra el botón verde "Merge pull request" → "Confirm merge".
  2. En GitHub Desktop: "Current Branch" → main → clic en "Fetch origin" (trae el cambio ya fusionado a tu computadora).
  3. (Opcional) borra la rama que ya cumplió su propósito: clic derecho sobre ella en "Current Branch" → "Delete".

E. Resolver un conflicto de fusión (merge conflict)

Ocurre cuando dos ramas cambiaron la misma línea de un archivo. GitHub marca el archivo con estas tres señales dentro del texto:

<<<<<<< HEAD
(el contenido que ya existe en main)
=======
(el contenido que trae tu rama)
>>>>>>> nombre-de-tu-rama
  1. Abre el archivo marcado en VS Code (GitHub Desktop lo señala en rojo con "Conflicts found").
  2. Decide qué contenido conservar: uno de los dos, o una combinación de ambos.
  3. Borra las tres marcas (<<<<<<<, =======, >>>>>>>) — deben desaparecer del archivo por completo, no solo el texto entre ellas.
  4. Guarda. En GitHub Desktop, el archivo pasa de "conflicto" a listo para confirmar.
  5. Escribe un mensaje (ej. "Resuelve conflicto en README") y clic en "Commit merge".
Nunca resuelvas un conflicto borrando todo el archivo o aceptando "lo que sea" sin leer — ambas versiones representan trabajo real de alguien.

F. README.md profesional — estructura mínima

Un README responde, en orden, "¿qué es esto?", "¿cómo lo uso?" y "¿quién lo hizo?". Plantilla mínima para el proyecto del curso:

# Nombre del proyecto

Breve descripción: qué hace y para qué entidad sin fines de lucro
(guardería, casa hogar, dispensario) está pensado.

## Funcionalidades

- Registro de beneficiarios/usuarios
- Gestión de datos (CRUD)
- Autenticación por perfiles y roles

## Tecnologías

Java, Spring Boot (a partir de la Semana 7)

## Cómo clonar y ejecutar

1. Clonar este repositorio
2. (Se completará semana a semana conforme el proyecto crezca)

## Autor

Tu nombre — Programación I, URL
No hace falta que todas las secciones estén completas hoy — el README crece con el proyecto. Lo importante es que la estructura ya exista y se mantenga actualizada.

G. Botones esenciales (tabla resumen)

Botón / acción en GitHub DesktopQué hace
"Current Branch"Muestra y cambia entre ramas
"Current Branch" → "New Branch"Crea una rama nueva y se mueve a ella
"Publish branch"Sube una rama nueva a GitHub (equivalente a "Publish repository" pero para ramas)
Branch → "Create Pull Request"Abre el navegador en github.com para proponer la fusión
"Merge pull request" (en github.com)Integra los cambios de la rama a la rama base (normalmente main)
"Fetch origin"Trae y combina cambios del remoto a tu copia local
Branch → "Merge into Current Branch..."Fusiona otra rama dentro de la rama activa, sin pasar por github.com
Archivo marcado "Conflicts found"Ese archivo necesita resolución manual antes del commit de fusión

H. Problemas comunes y su traducción

GitHub Desktop / GitHub muestra…Significa…
"This branch has conflicts that must be resolved"Otra rama ya cambió la misma línea; resuélvelo manualmente (sección E) antes de fusionar.
No aparece "Merge pull request"Faltan resolver conflictos, o alguien más debe aprobar primero según las reglas del repositorio.
"This branch is out-of-date with the base branch"main avanzó desde que creaste tu rama; conviene traer esos cambios antes de fusionar.
Botón "Commit merge" gris/deshabilitadoTodavía queda al menos un archivo marcado como "Conflicts found" sin resolver.
"There isn't anything to commit"No hay cambios nuevos que guardar — revisa que editaste y guardaste el archivo correcto.
