Las ramas tampoco son de Java

Igual que la semana pasada con Git, hoy no comparamos sintaxis: el flujo de ramas, Pull Requests y merges es el mismo en un proyecto de Python, Java o cualquier otro lenguaje. Esta guía conecta los clics de GitHub Desktop que practicaste hoy con el comando que hace lo mismo por debajo.
Buenas noticias si ya conoces Python
Si alguna vez viste en GitHub un proyecto de Python con ramas llamadas main, develop o feature/algo, ya viste esta misma convención — se usa igual sin importar el lenguaje. Un equipo de Python revisa Pull Requests exactamente como lo hiciste hoy tú.

1. Convención de nombres de ramas (universal)

No importa el lenguaje: los equipos suelen organizar sus ramas así.

RamaPara qué se usa (Python, Java, o cualquier otro)
mainLa versión estable, la que "cualquiera podría usar hoy"
development / developIntegra funcionalidades ya terminadas, antes de llegar a main
feature/nombre-cortoUna funcionalidad específica en construcción (ej. feature/login)
fix/nombre-cortoLa corrección de un error puntual
Esta misma convención la usarás en tu proyecto real desde hoy: ver Proyecto.

2. Lo que ya sabes hacer con GitHub Desktop: traducción a comandos

Esta semana aprendiste primero el "clic" (GitHub Desktop). Aquí ves qué comando hace exactamente lo mismo por debajo.

Acción en la interfaz gráficaComando equivalente en terminal
"Current Branch" → "New Branch"git checkout -b nombre-rama
"Publish branch"git push -u origin nombre-rama
Branch → "Create Pull Request"No hay comando local puro (se hace en GitHub.com), aunque existe la herramienta gh pr create de la CLI oficial de GitHub
"Merge pull request" (en github.com)git merge nombre-rama (si se hiciera de forma local, en vez de por la web)
Archivo marcado "Conflicts found"Editar el archivo, borrar las marcas <<<<<<</=======/>>>>>>>, luego git add archivo y git commit
"Fetch origin"git pull
Ninguna es "mejor": los equipos profesionales usan ambas según el momento. Conocer también el comando te sirve para trabajar en cualquier servidor sin interfaz gráfica y es el estándar que asume cualquier tutorial o compañero de trabajo.

3. Ejercicios de traducción: de la acción al comando

Traducción 1 — App de lista de tareas (to-do)

Quieres agregar la funcionalidad "marcar tarea como completada" sin tocar la versión que ya funciona.

Solución 
git checkout -b feature-marcar-completada
Crea la rama y te mueve a ella en un solo paso — igual que "New Branch" en GitHub Desktop.

Traducción 2 — Agenda de turnos de una clínica dental

Ya hiciste commit en tu rama feature-recordatorios. ¿Qué falta para que exista en GitHub y puedas abrir una Pull Request?

Solución 
git push -u origin feature-recordatorios
Después de esto, la Pull Request se crea desde github.com (o con gh pr create si tienes la CLI de GitHub instalada).

Traducción 3 — Reproductor de música (playlist)

Al fusionar tu rama feature-orden-aleatorio, aparece un archivo con marcas <<<<<<< HEAD. Describe los pasos, en orden, para resolverlo.

Solución
1) Abrir el archivo y decidir qué contenido conservar. 2) Borrar las tres marcas de conflicto por completo. 3) Guardar. 4) git add archivo. 5) git commit (sin -m a veces abre un editor para el mensaje de merge, que ya viene sugerido).

Traducción 4 — Reto inverso: ¿qué pasó aquí?

Un compañero ejecutó estos comandos seguidos. Describe en una frase qué logró:

git checkout -b feature-blog
git add .
git commit -m "Agrega sección de blog"
git push -u origin feature-blog
Solución
Creó una rama nueva llamada feature-blog, confirmó un cambio con un mensaje claro, y la subió a GitHub — lista para abrir una Pull Request hacia main desde el navegador.
Para el ticket de salida
En una frase: "¿Por qué crees que casi todos los proyectos profesionales, sin importar el lenguaje, usan ramas y Pull Requests en vez de editar directo en main?"
