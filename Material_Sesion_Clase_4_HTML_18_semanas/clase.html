Semana 4 — Ramas, colaboración y documentación

Sábado 1 de agosto de 2026 · 11:10–12:20 · En línea · Requiere GitHub Desktop (Semana 3) y el repositorio de la Guía 3 ya publicado en GitHub.
Abrir GitHub

Objetivos (hoy)

  • Explicar qué es una rama (branch) y por qué main debe permanecer siempre estable.
  • Crear una rama, trabajar en ella y hacer commits sin afectar main.
  • Abrir una Pull Request y dar/recibir retroalimentación de código con respeto.
  • Fusionar (merge) una Pull Request y resolver un conflicto básico.
  • Redactar un README.md profesional que documente el proyecto.

Normas rápidas

  • Nunca trabajes directo en main para un cambio nuevo: primero crea una rama.
  • Una Pull Request no es solo "para subir código": es una invitación a que alguien lo revise.
  • Al comentar el código de un compañero: sé específico, respetuoso y constructivo — nunca "esto está mal" sin explicar por qué.
  • Un conflicto de fusión no es un error tuyo: es normal cuando dos ramas cambian la misma línea.
Checklist antes de iniciar (docente)
  • Confirmar que todos tienen su repositorio de la Guía 3 publicado en GitHub.
  • Preparar de antemano dos ramas de ejemplo con un conflicto premeditado para la demo.
  • Tener a la mano una cuenta secundaria (o repositorio de ejemplo) para simular una Pull Request y su revisión.
  • Plan B listo por si GitHub.com está lento/caído (ver más abajo).

Guion minuto a minuto (70 min)

  1. Saluda y conecta con la Semana 3: "ya tu código vive en GitHub; hoy aprendes a cambiarlo sin miedo a romperlo".
  2. Comparte el enlace del Quiz de Presaberes (4 minutos, individual).
  3. Pregunta rápida: "¿qué harías si tu profesor te pidiera probar una idea nueva en tu proyecto, pero sin arriesgar la versión que ya funciona?"

Pregunta detonadora: "si editas directo tu proyecto real y tu cambio rompe todo, ¿qué le pasa a la versión que sí funcionaba?" → puente a: una rama (branch) es una copia paralela del proyecto donde puedes experimentar; main permanece intacta y estable mientras tanto.

  • Analogía: main es la versión "en producción" — la que todos ven. Una rama es un borrador privado que solo se integra cuando ya funciona.
  • Cada nueva funcionalidad, corrección o experimento merece su propia rama, con un nombre descriptivo (ej. feature-login, no prueba2).

Demostración en pantalla, en un repositorio de práctica nuevo ("practica-ramas"):

  1. GitHub Desktop → botón "Current Branch" (arriba, muestra la rama activa: main).
  2. Clic en "New Branch" → nombre feature-bienvenida → "Create Branch".
  3. GitHub Desktop mueve automáticamente a la nueva rama — el nombre en "Current Branch" cambia.
Disciplina en el flujo (valor de la semana)
main siempre debe poder mostrarse a alguien más sin vergüenza. Los experimentos y el trabajo a medias viven en ramas, nunca directo ahí.

Con feature-bienvenida activa, el flujo de commit es idéntico al de la Semana 3 — solo que ahora ocurre dentro de la rama:

  1. Repository → Open in Visual Studio Code, edita el README.md y guarda.
  2. GitHub Desktop → pestaña "Changes": el cambio aparece resaltado.
  3. Escribe el mensaje en "Summary" y clic en "Commit to feature-bienvenida" — nota que el botón ya no dice "main".
Error común: "se me olvidó en qué rama estaba"
Antes de editar cualquier archivo, mira siempre el botón "Current Branch" arriba. Si tu commit terminó en la rama equivocada, se puede mover con Branch → Move to Branch... desde el historial.
¿Cuántos commits puede tener una rama?
Los que necesites. Una rama puede vivir minutos (una corrección pequeña) o semanas (una funcionalidad grande) — lo importante es que represente una sola idea o funcionalidad completa antes de proponerla a main.

Con al menos un commit en la rama:

  1. Clic en "Publish branch" (sube la rama nueva a GitHub).
  2. Menú Branch → Create Pull Request (abre el navegador en github.com, ya en la comparación correcta).
  3. Verificar la dirección: base: main ← compare: feature-bienvenida — los cambios van HACIA main.
  4. Título claro + descripción: qué cambia y por qué. Clic en "Create pull request".

Simulación de revisión de código (con una segunda cuenta o repositorio de ejemplo del docente):

  • En la pestaña "Files changed" de la Pull Request, cualquiera con acceso puede dejar un comentario sobre una línea específica.
  • Comparar un comentario destructivo ("esto está mal") contra uno constructivo ("¿consideraste usar una constante aquí en vez de repetir el número? sería más fácil de mantener").
Colaboración y respeto (valor de la semana)
Revisar código no es buscar errores para "ganar": es ayudar a que el proyecto (y quien lo escribió) mejoren. Comenta el código, nunca a la persona.

  • Estirar manos y espalda, agua, mirar lejos de la pantalla 20 segundos.
  • Micro-check en el chat: "¿ya ves tu Pull Request en GitHub.com?"

Fusión sin conflicto (caso feliz):

  1. En la Pull Request de github.com, clic en "Merge pull request" → "Confirm merge".
  2. En GitHub Desktop: "Current Branch" → main → clic en "Fetch origin" (trae el cambio recién fusionado).
  3. (Opcional) borrar la rama que ya cumplió su propósito: clic derecho sobre ella en "Current Branch" → "Delete".

Ahora el caso con conflicto — demo preparada con dos ramas que editan la misma línea del README:

  1. Al intentar fusionar la segunda Pull Request, GitHub avisa: "This branch has conflicts that must be resolved".
  2. En GitHub Desktop, al hacer Branch → Merge into Current Branch..., el archivo en conflicto aparece marcado con <<<<<<< HEAD, una línea ======= y >>>>>>> nombre-rama.
  3. Abrir el archivo en VS Code, decidir qué contenido conservar (uno, el otro, o una combinación), y borrar manualmente las tres marcas de conflicto.
  4. Guardar, volver a GitHub Desktop: el archivo pasa de "conflicto" a listo para commit. Escribir un mensaje (ej. "Resuelve conflicto en README") y "Commit merge".
Un conflicto NO es un error de programación
Es Git avisando "dos personas cambiaron lo mismo, decide tú cuál versión es correcta". Nunca se resuelve borrando todo el archivo ni entrando en pánico.

  1. Comparte el enlace del Challenge — Ordena el flujo de colaboración.
  2. Modela el nivel Fácil en pantalla (1 min): crear rama y primer commit ahí.
  3. Los estudiantes resuelven Medio (Pull Request) y, si alcanza, Difícil (revisión + conflicto) — 7 min. Retroalimentación instantánea en toasts.
  4. Quien termine antes: continúa con los Ejercicios 6–8 en su propio repositorio de práctica.
Preguntas guía (docente, mientras circula por salas)
¿Por qué ese paso va antes de crear la Pull Request? ¿Qué pasaría si fusionas sin que nadie revise? ¿Cómo sabrías si tu proyecto tiene un conflicto ahora mismo?

  1. Comparte el enlace del Quiz de Final de Clase (10 preguntas, individual, 7 min).
  2. Al terminar, cada estudiante pulsa Calificar, revisa la retroalimentación y exporta su resultado a PDF.
  3. Los PDF del quiz y del challenge = evidencia de la Actividad en clase – Sesión 4.

  • Síntesis en 3 frases: experimenta en una rama, propón con una Pull Request, deja que main siempre funcione.
  • Ticket de salida en el chat: 1 aprendizaje + 1 duda.
  • Invitación a la evaluación anónima de la sesión.
  • Presenta la página Proyecto: hoy se crea la rama development del proyecto real y se documenta su README profesional.
  • Presenta el Entregable — Guía de Aprendizaje 4, fecha límite antes de la Sesión 5 (8 de agosto de 2026).
  • Puente a la semana 5: "hoy organizaste tu código con ramas; la próxima semana verás patrones de diseño y arquitectura web (MVC) para organizar el código dentro de cada archivo".
Plan B (si la tecnología falla)
Si una Pull Request tarda en cargar o GitHub.com está lento: practica el concepto de ramas y fusión en Learn Git Branching (simulador visual en el navegador, en español) mientras se restablece el servicio. Si ni siquiera hay internet estable: modela el conflicto en el pizarrón/chat con dos "versiones" de una misma frase y pide que decidan cuál combinar — el razonamiento es el mismo que resolver <<<<<<< HEAD.
