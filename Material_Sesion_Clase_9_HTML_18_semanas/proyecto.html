Proyecto · Guía 9 (1 pt) + ★ Entrega Parcial 2 (5 pts)

Tu app Spring Boot base, con MVC funcional, en GitHub

Primero la guía paso a paso para dejar tu proyecto en el estado que exige el hito, y al final la plantilla calificable. Fecha límite: antes de la Sesión 10 (19 de septiembre de 2026).
⚠️ Esta entrega cuenta doble
Una sola entrega, dos calificaciones: Guía de Aprendizaje 9 (1 pt, evaluación continua) y Avance del Proyecto — Entrega Parcial 2 (5 pts, hito de proyecto). No son dos plantillas distintas: completas esta página una vez y el mismo PDF sirve para ambas. Es la entrega individual con mayor peso de todo el primer tramo del curso.
Qué significa exactamente "app Spring Boot base con MVC funcional"
Es lo que pide el programa para esta entrega, y se traduce en cinco cosas concretas: (1) el proyecto arranca; (2) el código está organizado en paquetes (controller, service, model) y no todo suelto; (3) hay endpoints que responden; (4) hay un formulario web que los consume; (5) todo está en GitHub con README e historial de commits. No incluye base de datos (Semana 12), Thymeleaf (Semana 10) ni despliegue (Semana 14): no se evalúa lo que aún no se ha enseñado.

Parte guiada — deja tu proyecto listo para el hito

Paso 1 — Ubica tu punto de partida

Abre en VS Code tu proyecto real (el de las Semanas 7 y 8) y ejecútalo. Anota tu paquete base: es la línea package de tu archivo ...Application.java. Todo lo que crees hoy irá dentro de él.

# Ejemplo (el tuyo será distinto):
Paquete base : gt.edu.url.guarderiaesperanza
Carpeta base : src/main/java/gt/edu/url/guarderiaesperanza/
Clase principal: GuarderiaEsperanzaApplication.java
✅ Checkpoint: el proyecto arranca ("Started ... Application") y tienes anotado tu paquete base exacto.

Paso 2 — Crea las tres carpetas de la estructura MVC

Dentro de tu carpeta base (no fuera de ella), crea tres carpetas. En VS Code: clic derecho sobre la carpeta base → New Folder.

src/main/java/gt/edu/url/guarderiaesperanza/
├── GuarderiaEsperanzaApplication.java   (ya existía)
├── controller/     ← nueva
├── service/        ← nueva
└── model/          ← nueva
El error que hay que evitar aquí
Las tres carpetas van dentro de la carpeta que contiene tu ...Application.java. Si las creas al mismo nivel o más arriba, el proyecto compilará pero Spring no encontrará tus clases y las rutas responderán 404, sin ningún mensaje de error. Ver el Cheat Sheet, pestaña "Anatomía".
✅ Checkpoint: las tres carpetas existen dentro de tu paquete base.

Paso 3 — Crea tu clase de modelo

Archivo model/TuClase.java. Elige algo real de tu institución: Visitante, Nino, Paciente, Donante… Datos puros, sin anotaciones.

package gt.edu.url.guarderiaesperanza.model;   // ← tu paquete base + .model

public class Visitante {

    private String nombre;

    public Visitante(String nombre) {
        this.nombre = nombre;
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }
}
✅ Checkpoint: la clase no tiene errores en rojo. No lleva import ni anotaciones: es normal.

Paso 4 — Crea tu clase de servicio (la capa de negocio)

Archivo service/BienvenidaService.java. Aquí se decide qué dice tu aplicación: es la capa que la Semana 6 llamó "negocio".

package gt.edu.url.guarderiaesperanza.service;

import org.springframework.stereotype.Service;

import gt.edu.url.guarderiaesperanza.model.Visitante;

@Service
public class BienvenidaService {

    private static final String INSTITUCION = "Guardería Esperanza";  // ← tu institución real

    public String mensajeGeneral() {
        return "¡Bienvenido(a) a " + INSTITUCION + "!";
    }

    public String mensajePara(String nombre) {
        Visitante visitante = new Visitante(nombre);
        return "Hola, " + visitante.getNombre()
                + ". Gracias por visitar " + INSTITUCION + ".";
    }
}
✅ Checkpoint: la clase tiene @Service con su import, y el import de tu propia clase de modelo.

Paso 5 — Mueve y ajusta tu controlador

Si tu controlador de la Semana 8 quedó suelto junto a ...Application.java, muévelo a controller/ y corrige su línea package. Luego haz que delegue en el servicio en vez de armar el texto él mismo.

package gt.edu.url.guarderiaesperanza.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

import gt.edu.url.guarderiaesperanza.service.BienvenidaService;

@RestController
public class BienvenidaController {

    private final BienvenidaService bienvenidaService;

    public BienvenidaController(BienvenidaService bienvenidaService) {
        this.bienvenidaService = bienvenidaService;
    }

    @GetMapping("/api/saludo")
    public String saludo() {
        return bienvenidaService.mensajeGeneral();
    }

    @GetMapping("/api/bienvenida")
    public String bienvenida(@RequestParam(defaultValue = "visitante") String nombre) {
        return bienvenidaService.mensajePara(nombre);
    }
}
Por qué esto ya es "MVC funcional"
El controlador recibe la petición, el servicio decide la respuesta y el modelo guarda los datos. Cada capa hace una cosa. Eso es exactamente lo que se diseñó en las Semanas 5 y 6, ahora funcionando en código.
✅ Checkpoint: ejecutas el proyecto y ambas rutas responden con el nombre de tu institución real.

Paso 6 — Verifica tu formulario web

Confirma que existe src/main/resources/static/index.html con el formulario de la Semana 8, apuntando a tu endpoint. Si te falta, cópialo completo del Kit de archivos (archivos 10 y 11) — incluye también el CSS, que suma en la evaluación entre pares.

✅ Checkpoint: en localhost:8080 aparece tu formulario y, al enviarlo, el mensaje aparece sin recargar la página.

Paso 7 — README y .gitignore

Dos archivos pequeños que pesan mucho en la rúbrica y en el peer review. Ambos están completos en el Kit (archivos 8 y 9): copia, pega y reemplaza los datos entre corchetes por los tuyos.

  • README.md: qué es el proyecto, tecnologías, cómo ejecutarlo, tabla de endpoints y tu nombre.
  • .gitignore: evita subir la carpeta target/, que hace pesar el repositorio de más.
✅ Checkpoint: al abrir tu repositorio en GitHub.com, el README se ve formateado en la página principal y no aparece la carpeta target/.

Paso 8 — Publica y verifica como lo haría otra persona

Haz commit y push a tu rama development. Después, la prueba definitiva:

git add .
git commit -m "Organiza el proyecto en capas: modelo, servicio y controlador"
git push origin development

Prueba final: abre tu repositorio en GitHub.com como si fueras otra persona. ¿Se entiende qué es el proyecto? ¿Están los archivos de las tres capas? ¿El README explica cómo ejecutarlo? Eso es exactamente lo que verá quien te evalúe en el peer review.

✅ Checkpoint: tu rama en GitHub muestra las carpetas controller, service, model y static, más el README.
