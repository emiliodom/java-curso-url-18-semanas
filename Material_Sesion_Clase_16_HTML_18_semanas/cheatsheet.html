1. El Árbol Canónico de un Proyecto Spring Boot

En Java y Spring Boot, la regla de oro es: la ruta de carpetas debe coincidir exactamente con la declaración package. Si un archivo está fuera de su carpeta o fuera del paquete base, Spring no lo registrará.

2. Responsabilidades y Anotaciones Clave por Archivo
Capa / ArchivoAnotaciones principalesResponsabilidad única¿Qué pasa si falla o falta?
Entidad (Model)
Beneficiario.java		 @Entity, @Id, @GeneratedValue, @NotBlank, @NotNull Representa la tabla en Neon PostgreSQL y define qué datos son válidos. Hibernate no crea la tabla o se guardan registros corruptos en blanco.
Repositorio
...Repository.java		 @Repository (opcional), extends JpaRepository<T, ID> Provee métodos CRUD listos (save, findAll, findById, deleteById) sin escribir SQL a mano. Spring no puede inyectar el bean (NoSuchBeanDefinitionException).
Servicio
...Service.java		 @Service, @Autowired Aislar al controlador de la base de datos; aplica reglas de negocio antes de persistir. Alto acoplamiento: el controlador asume demasiadas responsabilidades.
Controlador
...Controller.java		 @Controller, @GetMapping, @PostMapping, @Valid Recibe la petición HTTP, llena el modelo, ejecuta validaciones y decide qué vista retornar o si redirige. Error 404 (ruta no encontrada) o 405 (método POST no soportado).
Vistas
templates/*.html		 th:object, th:field, th:errors, sec:authorize Renderiza la interfaz dinámica en el navegador, mostrando datos y errores. Error 500 (TemplateProcessingException) si una expresión ${...} está mal escrita.
Seguridad
SecurityConfig.java		 @Configuration, @EnableWebSecurity Define qué rutas son públicas (permitAll) y cuáles requieren rol ADMIN. Todas las rutas quedan bloqueadas o la app queda expuesta sin autenticación.
El Ciclo de Vida de una Petición Web en Spring Boot (Paso a Paso)

Sigue la secuencia exacta de lo que ocurre cuando un usuario abre un formulario y guarda un registro:

Fase 1: Petición GET (Cargar Formulario)
  1. El usuario hace clic en "Nuevo Registro" (Navegador solicita GET /beneficiarios/nuevo).
  2. El Controlador atiende con @GetMapping("/nuevo").
  3. Se crea el objeto vacío: model.addAttribute("beneficiario", new Beneficiario()); para que Thymeleaf tenga a qué enlazar los inputs.
  4. Retorno de plantilla: return "formulario";.
  5. Thymeleaf procesa: busca templates/formulario.html, vincula th:object="${beneficiario}" y envía el HTML final al navegador con los campos limpios.
Fase 2: Petición POST (Envío de Datos)
  1. El usuario envía el formulario: <form th:action="@{/beneficiarios/guardar}" method="post">.
  2. Spring Security valida el token CSRF invisible generado en el formulario.
  3. Data Binding automático: Spring toma los inputs (name="nombre", etc.) y los asigna a la instancia de Beneficiario con sus setters.
  4. Bean Validation: Se disparan las anotaciones (@NotBlank, @Min, etc.) marcadas con @Valid.
  5. Los resultados se almacenan: Spring inyecta el resultado inmediatamente en BindingResult result.
Fase 3A: Escenario con Errores de Validación

Condición: if (result.hasErrors()) es VERDADERO.

  • NO se llama al repositorio: repositorio.save() nunca se ejecuta.
  • Regla de oro: Se retorna el nombre de la plantilla directamente: return "formulario";.
  • ¿Por qué NO usar redirect?: Porque una redirección crearía una petición HTTP nueva y borraría los mensajes de error y los textos que el usuario ya escribió.
  • Thymeleaf renderiza: th:errors="*{campo}" muestra el mensaje rojo y th:errorclass="is-invalid" pinta el borde del input.
Fase 3B: Escenario Exitoso y Persistencia

Condición: result.hasErrors() es FALSO.

  • Invocación de persistencia: servicio.guardar(beneficiario) o repositorio.save(beneficiario).
  • Hibernate (ORM): Traduce el objeto Java a una instrucción SQL INSERT INTO beneficiarios (...) VALUES (...) y la envía por red cifrada a Neon PostgreSQL.
  • Patrón POST-Redirect-GET (PRG): El método finaliza con return "redirect:/beneficiarios";.
  • Navegador recibe HTTP 302 y solicita un nuevo GET /beneficiarios.
  • Ventaja crítica: Si el usuario pulsa F5 (Refrescar), no duplica el registro en la base de datos.
1. El Concepto Central: Vincular Registros Guardando solo el ID (Cero Complejidad)

Muchos estudiantes se traban intentando configurar relaciones JPA complejas (@ManyToOne, @OneToMany, FetchType, etc.). En este curso aplicamos la regla de oro de la ingeniería pragmática: cada entidad sigue siendo una tabla plana, y para vincular dos registros guardamos simplemente el ID como un campo numérico normal.

2. Módulo 1: Asignación a Equipos (/asignacion-equipo)

Permite al ADMIN tomar cualquier jugador registrado y asignarlo a un equipo disponible validando cupos en el Servicio.

A) La Entidad Equipo (model/Equipo.java)
@Entity
public class Equipo {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 40)
    private String nombre;

    @Column(nullable = false)
    private Integer cupo; // Cuántos jugadores caben en la plantilla

    // Constructor vacío, constructor con campos, getters y setters
}
B) El Controlador Dinámico (controller/AsignacionController.java)
@Controller
public class AsignacionController {
    private final JugadorService jugadorService;
    private final EquipoService equipoService;

    // GET: Carga jugadores y equipos reales para poblar los <select>
    @GetMapping("/asignacion-equipo")
    public String ver(Model model) {
        model.addAttribute("jugadores", jugadorService.listarTodos());
        model.addAttribute("equipos", equipoService.listarTodos());
        return "asignacion-equipo";
    }

    // POST: Recibe los IDs seleccionados por el usuario
    @PostMapping("/asignacion-equipo")
    public String asignar(@RequestParam Long jugadorId,
                          @RequestParam(required = false) Long equipoId,
                          Model model) {
        try {
            equipoService.asignar(jugadorId, equipoId);
        } catch (IllegalStateException e) {
            model.addAttribute("error", e.getMessage());
            return ver(model); // Con error NO hay redirect para conservar el mensaje
        }
        return "redirect:/asignacion-equipo?ok";
    }
}
C) Formulario Dinámico en Thymeleaf (templates/asignacion-equipo.html)

3. Módulo 2: Estadísticas de Jugador (/estadisticas-jugador)

Permite seleccionar un jugador ya registrado y cargar/actualizar sus métricas (partidos, goles, asistencias). Muestra cómo manejar un selector dinámico en cascada.

A) Patrón de Búsqueda y Carga Automática en el Controlador
@GetMapping("/estadisticas-jugador")
public String ver(@RequestParam(required = false) Long jugadorId, Model model) {
    EstadisticaJugador form = new EstadisticaJugador();
    if (jugadorId != null) {
        // Si el jugador ya tiene estadísticas guardadas, las carga para editarlas
        form = estadisticaService.buscarPorJugador(jugadorId).orElseGet(() -> {
            EstadisticaJugador nueva = new EstadisticaJugador();
            nueva.setJugadorId(jugadorId);
            return nueva;
        });
    }
    model.addAttribute("estadistica", form);
    model.addAttribute("jugadores", jugadorService.listarTodos());
    model.addAttribute("estadisticas", estadisticaService.listarTodas());
    return "estadisticas-jugador";
}
B) Selector que Recarga la Vista (templates/estadisticas-jugador.html)

4. Módulo 3: El Hub Personal del Jugador (/mi-hub) con Círculos y Vacantes

Cuando un usuario con rol ROLE_JUGADOR inicia sesión, el sistema lo envía a su propio Hub. Allí ve su ficha, la plantilla de su equipo (con círculos de colores y "Vacante" si el cupo no se ha llenado) y sus estadísticas personales.

A) Cómo saber quién está conectado (HubJugadorController.java)
@GetMapping("/mi-hub")
public String hub(Principal principal, Model model) {
    // 1. Principal.getName() nos da el 'username' con el que inició sesión
    Jugador yo = jugadorService.buscarPorUsername(principal.getName()).orElse(null);
    model.addAttribute("yo", yo);

    if (yo != null && yo.getEquipoId() != null) {
        Equipo equipo = equipoService.buscarPorId(yo.getEquipoId());
        List<Jugador> casillas = new ArrayList<>(equipoService.plantilla(equipo.getId()));
        
        // 2. Si hay menos jugadores que el cupo, rellenamos con null para dibujar "Vacante"
        while (casillas.size() < equipo.getCupo()) {
            casillas.add(null);
        }
        model.addAttribute("equipo", equipo);
        model.addAttribute("casillas", casillas);
    }
    return "hub-jugador";
}
B) Renderizado de la Plantilla con Círculos (templates/hub-jugador.html)
<ul class="plantilla">
  <li th:each="c : ${casillas}">
    <!-- Si la casilla tiene jugador: círculo con la inicial del nombre -->
    <span th:if="${c != null}" class="circulo" th:classappend="${c.id == yo.id} ? 'yo'"
          th:text="${#strings.substring(c.nombre, 0, 1)}">A</span>

    <!-- Si la casilla es null: círculo punteado de vacante con un signo más -->
    <span th:if="${c == null}" class="circulo vacante">+</span>

    <span th:text="${c != null} ? ${c.nombre} : 'Vacante'">Nombre</span>
  </li>
</ul>

5. Seguridad y Redirección tras el Login

Para que el jugador no vea la lista administrativa ni botones de editar/borrar, agregamos una bifurcación en JugadorController y permisos estrictos en SecurityConfig:

// En JugadorController.java:
@GetMapping({"/", "/jugadores"})
public String listar(Model model, Authentication auth) {
    boolean esJugador = auth.getAuthorities().stream()
            .anyMatch(a -> a.getAuthority().equals("ROLE_JUGADOR"));
    if (esJugador) {
        return "redirect:/mi-hub"; // Jugador entra directo a su Hub
    }
    model.addAttribute("jugadores", jugadorService.listarTodos());
    return "lista";
}

// En SecurityConfig.java:
.requestMatchers("/asignacion-equipo").hasRole("ADMIN")
.requestMatchers("/estadisticas-jugador").hasAnyRole("ADMIN", "ENTRENADOR")
.requestMatchers("/mi-hub").hasRole("JUGADOR")
1. Cómo incluir Imágenes en el Proyecto (Carpeta static)

Spring Boot trata todo archivo dentro de src/main/resources/static/ como un archivo público accesible directamente desde la raíz del servidor web. No necesitas configurar controladores ni rutas Java para servir imágenes.

A) Ubicación en el Árbol del Proyecto
mi-proyecto/
└── src/main/resources/
    ├── static/
    │   ├── estilos.css
    │   └── img/
    │       ├── logo.png             <-- Se accede en http://localhost:8080/img/logo.png
    │       ├── escudo.svg           <-- Se accede en http://localhost:8080/img/escudo.svg
    │       └── foto-instalaciones.jpg
    └── templates/
        └── lista.html
B) Sintaxis Canónica en Thymeleaf

Usa siempre th:src="@{/img/nombre.png}". La arroba @{...} asegura que la ruta funcione tanto en tu computadora local como en Render tras el proxy reverso:

<!-- Imagen fija (logotipo o banner) -->
<img th:src="@{/img/escudo.svg}" alt="Logotipo Escuela Los Cerritos" width="60" height="60">

<!-- Imagen dinámica si la entidad guarda el nombre del archivo en la base de datos -->
<img th:src="@{'/img/' + ${jugador.fotoArchivo}}" alt="Foto de perfil" class="avatar">
⚠️ Trampa habitual con Spring Security

Si agregas una carpeta nueva como /img/ y tu aplicación tiene Spring Security activo, la imagen te dará error 403 (candado roto). Para solucionarlo, agrega la ruta pública a SecurityConfig.java:

.requestMatchers("/login", "/estilos.css", "/img/**", "/error").permitAll()
2. Videos de YouTube Embebidos con <iframe> (Cero Dependencias)

Para el entregable final llave en mano (videos explicativos) o demostraciones institucionales, puedes embeber reproductores de YouTube oficiales directamente en cualquier vista Thymeleaf usando un <iframe> estándar sin instalar ninguna librería.

A) La Regla de Oro de la URL de Embebido
Tipo de URLFormato¿Funciona en <iframe>?
URL de Navegador (Normal) https://www.youtube.com/watch?v=dQw4w9WgXcQ ❌ Falla. YouTube bloquea la inserción directa por seguridad.
URL de Embebido (Embed) https://www.youtube.com/embed/dQw4w9WgXcQ ✅ Funciona perfectamente en cualquier navegador y celular.

Si tu entidad (por ejemplo un Proyecto, Taller o Beneficiario) guarda el ID del video en una columna, concaténalo con Thymeleaf:

        style="width: 100%; aspect-ratio: 16/9; border: 0; border-radius: 8px;"
        allowfullscreen>
</iframe>

El Ciclo de Mantenimiento Continuo: Cambio → Push → Redeploy

En la nube moderna (PaaS como Render), el mantenimiento no requiere acceder por SSH ni subir archivos por FTP. Todo se gobierna desde Git:

Paso 1: Modificación Local

Realizas el cambio en tu editor (ej. corregir una etiqueta en formulario.html o ajustar una regla de validación). Pruebas en tu máquina local si lo deseas.

Paso 2: Commit y Push 
git add .
git commit -m "fix(qa): corregir mensaje de validacion y alinear botones"
git push origin main
El push envía los nuevos commits al repositorio remoto en GitHub.
Paso 3: Webhook y Detección en Render

GitHub notifica a Render inmediatamente mediante un webhook. Render pone el deploy en estado In progress y comienza a ejecutar el Dockerfile de dos etapas.

Paso 4: Empaquetado y Reemplazo sin Caída

Maven compila y empaqueta el nuevo .jar. Render apaga el contenedor viejo únicamente cuando el nuevo contenedor pasa la prueba de arranque (Healthcheck en el puerto ${PORT}).

Paso 5: Verificación en Producción

Refrescas tu URL pública https://...onrender.com y constatas que el cambio ya está visible para el cliente y los usuarios finales.

⚠️ Trampas frecuentes en el Redeploy de Render
  • Olvido de push a main: Hiciste el commit pero se quedó en tu computadora local o en una rama secundaria (development). Render solo escucha main.
  • Error de compilación en Maven: Si un import o llave quedó rota, el log de Render mostrará BUILD FAILURE y conservará la versión previa en línea.
  • Variables de entorno: Recuerda que Render nunca lee tu disco local; las contraseñas y la DB_URL viven en el panel Environment de Render.
