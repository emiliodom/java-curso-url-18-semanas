Laboratorio Práctico de QA

Batería de Pruebas Funcionales y Diagnóstico Arquitectónico

Aplica estos 6 casos de prueba estructurados sobre tu proyecto. Cada ejercicio te explica qué capas se están activando y dónde revisar en tu código si algo no responde como se espera.

CP-01 · Presentación Capa: Controlador + Vistas Thymeleaf

Carga Limpia del Formulario de Registro (Petición GET)

Objetivo: Comprobar que la ruta /nuevo entrega el formulario sin errores y con los campos listos para captura.

Ruta arquitectónica activada:
Navegador (GET /nuevo) ➔ Controlador (@GetMapping) ➔ model.addAttribute("entidad", new Entidad()) ➔ templates/formulario.html (th:object).
  1. Abre tu navegador e ingresa a la URL de creación (ej. https://tu-app.onrender.com/beneficiarios/nuevo o en localhost).
  2. Verifica que la página responda con código HTTP 200 (sin pantalla de error blanca ni 404).
  3. Comprueba que todos los campos del formulario aparezcan completamente vacíos y sin mensajes de error precargados.
🔍 ¿Qué revisar en tu código si este caso falla?
  • Error 404: Verifica que tu clase controladora tenga la anotación @Controller (y no @RestController) y que esté dentro del paquete base (ej. gt.edu.url.miproyecto.controller).
  • Error 500 (Neither BindingResult nor plain target object available): En el controlador olvidaste hacer model.addAttribute("nombreEntidad", new Entidad()) con el mismo nombre que pusiste en th:object="${nombreEntidad}" en el HTML.
CP-02 · Validación y UX Capa: Bean Validation + BindingResult

Rechazo de Datos Inválidos y Retención de Valores (Petición POST)

Objetivo: Verificar que la aplicación rechace entradas vacías o fuera de rango sin caerse y sin borrar lo que el usuario escribió.

Ruta arquitectónica activada:
Formulario POST ➔ Controlador (@Valid @ModelAttribute) ➔ BindingResult.hasErrors() = true ➔ return "formulario" (SIN redirect) ➔ th:errors.
  1. En el formulario abierto, deja un campo obligatorio en blanco (ej. Nombre).
  2. Ingresa un valor intencionalmente inválido en un campo numérico (ej. Edad = -10 o fecha futura si no es permitida).
  3. Presiona el botón "Guardar" o "Registrar".
  4. Resultado esperado: El formulario debe recargarse en la misma pantalla mostrando alertas en color rojo al lado de cada campo erróneo. Los datos válidos que sí escribiste deben permanecer en sus casillas (no desaparecer).
🔍 ¿Qué revisar en tu código si este caso falla?
  • Se guardó basura en la base de datos: Te faltó colocar @Valid antes del parámetro en el método del controlador, o tu entidad carece de las anotaciones de validación (@NotBlank, @Min, etc.).
  • Los campos se limpiaron por completo: En tu controlador hiciste return "redirect:/nuevo" en lugar de devolver directamente la vista return "formulario". El redirect destruye el estado de la petición.
  • Error 500 al enviar: Revisa el orden de los parámetros en el controlador. BindingResult DEBE ir inmediatamente después del objeto validado; si colocas otro parámetro en medio (como Model), Spring Boot explota.
CP-03 · Persistencia Capa: Servicio + JpaRepository + Neon DB

Guardado Exitoso y Redirección POST-Redirect-GET

Objetivo: Confirmar que un registro con todos los datos correctos se almacene en Neon PostgreSQL y que la app redirija a la lista sin duplicar al refrescar.

Ruta arquitectónica activada:
Formulario POST válido ➔ repositorio.save(entidad) ➔ Hibernate SQL INSERT ➔ Neon DB ➔ return "redirect:/beneficiarios" ➔ Navegador GET /beneficiarios.
  1. Llena el formulario con datos de prueba realistas (ej. Nombre: "Ana Morales", Edad: 8, teléfono válido).
  2. Presiona "Guardar".
  3. Verifica que la URL cambie automáticamente a la lista (ej. /beneficiarios) y que el nuevo registro aparezca en la tabla.
  4. Pulsa la tecla F5 (Refrescar) en el navegador: no debe aparecer ninguna advertencia de "Reenviar formulario" ni duplicarse la fila.
🔍 ¿Qué revisar en tu código si este caso falla?
  • Falla de conexión a base de datos: Si sale error 500 con PSQLException: Connection refused, verifica que en Render la variable DB_URL tenga sslmode=require y que la base de datos Neon no esté en error de credenciales.
  • Al refrescar pregunta si reenviar: El controlador retornó la vista lista directamente return "lista" en vez de usar return "redirect:/beneficiarios".
CP-04 · Listado Dinámico Capa: JpaRepository + Thymeleaf th:each

Consulta y Renderizado de Lista Dinámica (Petición GET)

Objetivo: Validar que todos los registros de la base de datos se consulten eficientemente y se muestren ordenados en una tabla HTML.

Ruta arquitectónica activada:
Navegador (GET /beneficiarios) ➔ repositorio.findAll() ➔ model.addAttribute("lista", ...) ➔ templates/lista.html (th:each="item : ${lista}").
  1. Ingresa a la pantalla principal del listado (ej. /beneficiarios).
  2. Cuenta las filas visibles en pantalla y compáralas con los registros existentes.
  3. Verifica que los formatos de fecha, moneda o números enteros no muestren valores null.
🔍 ¿Qué revisar en tu código si este caso falla?
  • La tabla sale vacía a pesar de haber datos: Verifica que en el controlador la variable agregada al modelo tenga exactamente el mismo nombre usado en el HTML: model.addAttribute("beneficiarios", repo.findAll()) coincide con th:each="b : ${beneficiarios}".
  • Error al acceder a propiedades: Si sale Property or field 'nombre' cannot be found on object, revisa que tu clase entidad tenga los métodos getter públicos (getNombre()) correspondientes.
CP-05 · Seguridad Capa: Spring Security + SecurityFilterChain

Protección de Rutas y Control de Acceso por Rol

Objetivo: Asegurar que las rutas críticas de edición y eliminación estén protegidas y requieran autenticación previa.

Ruta arquitectónica activada:
Petición a /beneficiarios/eliminar/{id} ➔ SecurityFilterChain ➔ Verificación de Rol ADMIN ➔ Si no autenticado: redirect /login ➔ Si autenticado sin rol: 403 /acceso-denegado.
  1. Abre una ventana de incógnito (sin sesión iniciada) e intenta ingresar directamente por URL a /beneficiarios/nuevo.
  2. Resultado esperado 1: La aplicación debe redirigirte de inmediato a la pantalla de /login.
  3. Inicia sesión con un usuario estándar (ej. rol ENTRENADOR o VOLUNTARIO). Verifica que no aparezca el botón "Eliminar" (oculto por sec:authorize).
  4. Intenta forzar la eliminación escribiendo la URL directa en el navegador. Resultado esperado 2: Pantalla de acceso denegado (código HTTP 403).
🔍 ¿Qué revisar en tu código si este caso falla?
  • Cualquier usuario puede borrar: Te confiaste solo en ocultar el botón en el HTML (sec:authorize). Recuerda que la verdadera seguridad está en SecurityConfig.java configurando requestMatchers("/beneficiarios/eliminar/**").hasRole("ADMIN").
  • La app da error 405 en acceso denegado: Si el controlador de /acceso-denegado está marcado con @GetMapping, fallará cuando un POST sea rechazado. Debe ser @RequestMapping("/acceso-denegado") para admitir cualquier método HTTP.
CP-06 · Operaciones Capa: Git + Webhooks + Render CI/CD

Ciclo de Mantenimiento Continuo (Push a Main ➔ Redeploy en Render)

Objetivo: Comprobar el pipeline automatizado de entrega continua modificando un elemento visual y verificándolo publicado en la nube.

Ruta arquitectónica activada:
Edición local ➔ git commit ➔ git push origin main ➔ Render Webhook ➔ Docker Build ➔ Deploy Live.
  1. En tu proyecto local, realiza una mejora visible en la plantilla de créditos o en el pie de página de tu lista (ej. agregar "Versión 1.0 — QA Verificado").
  2. Haz commit y push a la rama principal: git commit -am "QA: mejora visual de cierre" y git push origin main.
  3. Abre el panel de control de Render en tu navegador y observa la pestaña Logs de tu Web Service.
  4. Monitorea cómo Render detecta el nuevo commit, descarga las capas Docker, ejecuta Maven y finaliza con el mensaje "==> Your service is live 🎉".
  5. Recarga tu aplicación en la URL pública https://...onrender.com y constata que el cambio ya está disponible para el mundo.
🔍 ¿Qué revisar si el Redeploy falla en Render?
  • El deploy no inicia: Verifica si hiciste push a main o a otra rama. Render en su configuración tiene asignada la rama de despliegue (generalmente main).
  • Build failure en Maven: Si el log muestra Failed to execute goal ... test, recuerda que en el Dockerfile se debe usar mvn clean package -DskipTests para evitar que las pruebas de integración intenten buscar bases de datos locales inexistentes en el contenedor.
