Ejercicios · Semana 14 · En tu computadora, en Neon y en Render (todo real)

Publica la Escuela de Fútbol en internet, una pieza a la vez

Tres pestañas: ocho ejercicios en escalera con taller-formularios y Jugador, el Kit con los archivos completos que cambian, y los errores reales que vas a provocar y leer.
La idea de hoy, con una mudanza
Publicar una aplicación se parece a mudar una escuela a un edificio nuevo. Primero empacas todo en cajas (el .jar). Luego consigues el archivo donde se guardarán los expedientes (la base de datos en Neon). Después le das al nuevo edificio las instrucciones para armar todo (el Dockerfile) y le entregas las llaves en sobre cerrado (las variables de entorno en Render). Al final recorres el edificio para comprobar que todo funciona (la verificación). Ningún mueble se rediseña: solo cambia el lugar.
Elige tu ruta (una sola)
Ruta A — continúas tu taller-formularios de la Semana 13 (con login y roles). Haces los ejercicios en orden.
Ruta B — no tienes el proyecto o quedó roto. Genera el proyecto con el Kit de la Semana 13 (todos los archivos Java y plantillas) y luego agrega los archivos de la pestaña 2 de esta página. Necesitas una cuenta de GitHub con el proyecto subido antes del ejercicio 6.
Reglas de trabajo de hoy
1) Una pieza a la vez. Primero el .jar en tu PC, luego tu PC con Neon, y solo al final Render. Así, si algo falla, el culpable es la última pieza.
2) Las claves de Neon nunca van a un archivo del proyecto. Guárdalas en un lugar privado fuera de la carpeta (un gestor de contraseñas o una nota personal), nunca en GitHub ni en el chat de la clase.
3) Lee el log. Cuando algo falle, busca la línea que dice PSQLException o el primer Caused by: con un mensaje entendible. El último Caused by a veces engaña (ver la pestaña de errores).
4) Los nombres de botones de esta página se comprobaron en octubre de 2026. Si una pantalla se ve un poco distinta, busca la palabra en negrita: los nombres cambian menos que los colores.

Ejercicio 1 — Empaca tu aplicación en un .jar Nivel 1 · Observar

💻 TU PC Terminal de VS Code, dentro de la carpeta taller-formularios.

Qué es un .jar: un solo archivo que contiene todo lo necesario para que tu aplicación funcione: tu código compilado, Spring, el servidor web Tomcat, el driver de PostgreSQL. Es como una lonchera armada: quien la recibe no necesita cocinar, solo abrirla. Por eso no hace falta instalar un servidor aparte (el viejo archivo .war).

  1. Detén la aplicación si está corriendo (Ctrl+C). Abre una terminal nueva (sin variables definidas).
  2. Ejecuta: 
    # Windows (PowerShell)
.\mvnw.cmd clean package

# macOS / Linux / Git Bash
./mvnw clean package
  3. Va a fallar, y está bien. Busca en el texto rojo esta línea:
    [ERROR] TallerFormulariosApplicationTests.contextLoads » IllegalState Failed to load ApplicationContext ... Caused by: org.springframework.util.PlaceholderResolutionException: Could not resolve placeholder 'ADMIN_PASSWORD' in value "${ADMIN_PASSWORD}" [ERROR] BUILD FAILURE
    ¿Por qué? Spring Initializr creó una prueba llamada contextLoads que arranca la aplicación completa para ver si enciende. Y desde la Semana 13 tu aplicación se niega a arrancar sin las contraseñas. La prueba está haciendo su trabajo.
  4. Define las dos variables de la Semana 13 en esa misma terminal y repite: 
    # Windows (PowerShell)
$env:ADMIN_PASSWORD = "Clave-Admin-2026"
$env:ENTRENADOR_PASSWORD = "Clave-Entr-2026"
.\mvnw.cmd clean package

# macOS / Linux / Git Bash
export ADMIN_PASSWORD="Clave-Admin-2026"
export ENTRENADOR_PASSWORD="Clave-Entr-2026"
./mvnw clean package
    Ahora debe terminar con BUILD SUCCESS. (Las claves son ejemplo: usa las tuyas.)
  5. Mira el resultado: en VS Code abre la carpeta target/. Ahí está taller-formularios-0.0.1-SNAPSHOT.jar (unos 60 MB: lleva todo adentro).
  6. Ejecútalo sin Maven y sin VS Code, como lo hará el servidor: 
    java -jar target/taller-formularios-0.0.1-SNAPSHOT.jar
    Abre http://localhost:8080, entra como admin y verás tus jugadores de siempre (sigue en perfil dev, con H2). Detén con Ctrl+C.
✅ Checkpoint: BUILD SUCCESS, existe el .jar en target/ y con java -jar la aplicación abre en el navegador.
¿Qué acabo de ver? (respuesta)
Viste las dos caras de empaquetar: (1) Maven prueba antes de empacar, y si una prueba falla no entrega la caja (eso es bueno: no se publica algo que no enciende); (2) el .jar se ejecuta con un solo comando, con su propio Tomcat adentro. Render hará exactamente esto, pero dentro de su propia máquina. Nota: DevTools (la recarga automática de la Semana 12) no viaja dentro del .jar: se desactiva sola en producción, tal como prometimos.

Ejercicio 2 — Un puerto que se adapta al lugar Nivel 1 · Modificar una línea

💻 TU PC Archivo src/main/resources/application.properties.

Por qué: en tu computadora la aplicación escucha en la "puerta" 8080. Render, en cambio, le dice a cada aplicación en qué puerta debe escuchar mediante una variable de entorno llamada PORT (normalmente 10000). Es como un salón de clases que cambia de número según el edificio: la aplicación debe preguntar "¿en qué salón me toca?" en vez de asumirlo.

  1. Agrega esta línea a application.properties (debajo de server.error.whitelabel.enabled=false): 
    # Puerto: Render entrega el suyo en la variable PORT; en tu computadora no existe y se usa 8080.
server.port=${PORT:8080}
    Se lee: "usa el valor de PORT; si no existe, usa 8080". Lo que va después de los dos puntos es el valor por defecto. Por eso, a diferencia de ${ADMIN_PASSWORD}, esta variable no es obligatoria.
  2. Reempaqueta (en la terminal que ya tiene las dos claves): ./mvnw clean package (o .\mvnw.cmd clean package).
  3. Prueba el puerto "prestado": 
    # Windows (PowerShell)
$env:PORT = "9090"
java -jar target/taller-formularios-0.0.1-SNAPSHOT.jar

# macOS / Linux / Git Bash
PORT=9090 java -jar target/taller-formularios-0.0.1-SNAPSHOT.jar
    En el log busca Tomcat started on port 9090 y abre http://localhost:9090. Detén la app. En PowerShell, borra la variable con Remove-Item Env:PORT para volver al 8080.
✅ Checkpoint: con PORT=9090 la app abre en el 9090; sin PORT, en el 8080.

¿Por qué está vacía si mi app ya tiene jugadores?
Porque tus jugadores viven en el archivo H2 de tu computadora (datos/). Neon es un archivo nuevo y distinto, en otro lugar. Los datos de práctica no se mudan: producción empieza limpia, como un cuaderno nuevo para el ciclo escolar.

Ejercicio 4 — Saca las 3 piezas de conexión Nivel 2 · Transformar

🐘 NEON 📝 una nota privada

Neon te da una sola cadena con todo junto (usuario, contraseña, dirección y base). Spring la necesita en tres piezas separadas, y la dirección escrita en el "idioma" de Java (JDBC). Es como recibir una dirección completa en un sobre y tener que pasarla a un formulario con casillas separadas.

console.neon.tech · Project dashboardMaqueta simplificada
1Connect to your branch
Branch · Computeproduction · Primary
Database · Roleneondb · neondb_owner
2Connection pooling apágalo (viene encendido)
3Mostrar contraseña👁 ícono del ojo / Show password
4Connection stringpostgresql://neondb_owner:npg_AbC123xYz@ep-cool-river-a1b2c3d4.us-east-2.aws.neon.tech/neondb?sslmode=require&channel_binding=require
Copy snippet
  • 1En el panel del proyecto pulsa el botón Connect. Se abre la ventana Connect to your branch. Deja la rama, la base y el rol como vienen.
  • 2Apaga Connection pooling. Con el interruptor encendido, la dirección lleva -pooler: es un "repartidor" de conexiones útil para miles de usuarios, pero recomendado no usarlo para crear tablas. Apagado te da la conexión directa, la más simple para nuestro proyecto.
  • 3Muestra la contraseña antes de copiar; si copias con asteriscos, copiarás asteriscos.
  • 4Copia la cadena y pégala en una nota privada (no en tu proyecto). El selector de lenguaje también ofrece Java; sirve, pero te pone usuario y clave dentro de la URL, y aquí los queremos separados.

Desarma la cadena (con colores)

postgresql://neondb_owner:npg_AbC123xYz@ep-cool-river-a1b2c3d4.us-east-2.aws.neon.tech/neondb?sslmode=require&channel_binding=require └─ protocolo ─┘└── usuario ──┘ └ contraseña ┘ └────────────── dirección del servidor ──────────────┘ └ base ┘ └──── opciones de seguridad ────┘
VariableCómo se armaEjemplo
DB_USERLo que está entre // y :neondb_owner
DB_PASSWORDLo que está entre : y @npg_AbC123xYz
DB_URLjdbc:postgresql:// + dirección + / + base + ?sslmode=require&channelBinding=requirejdbc:postgresql://ep-cool-river-a1b2c3d4.us-east-2.aws.neon.tech/neondb?sslmode=require&channelBinding=require
Tres detalles que importan: (1) DB_URL empieza con jdbc: y no lleva usuario ni contraseña. (2) sslmode=require obliga a cifrar la conversación con Neon: Neon no acepta conexiones sin cifrar. (3) En Java la opción se escribe channelBinding (sin guion bajo, con B mayúscula); en la cadena de Neon viene como channel_binding. Si la dejas con guion bajo, Java simplemente la ignora (lo comprobamos), pero escrita bien añade una protección extra.

¿Te da miedo equivocarte? En el Cheat Sheet, pestaña "🔑 Las 6 variables", hay un separador automático: pegas la cadena y te muestra las tres piezas. Funciona solo dentro de tu navegador; no envía nada a ningún lado.

✅ Checkpoint: en tu nota privada tienes DB_URL (empieza con jdbc:postgresql://, sin -pooler), DB_USER y DB_PASSWORD.

Ejercicio 6 — El Dockerfile: la receta que entenderá Render Nivel 3 · Crear con modelo

💻 TU PC 🐙 GITHUB

Qué es Docker, en simple: Render no sabe "cocinar" Java por su cuenta. Un Dockerfile es una receta escrita: "consigue una cocina con Java y Maven, mete los ingredientes, cocina el .jar, y sírvelo en un plato limpio con solo Java para ejecutarlo". Render sigue la receta al pie de la letra cada vez que publicas. El resultado (el "plato servido" que corre) se llama contenedor.

  1. En la raíz del proyecto (junto a pom.xml, no dentro de src) crea un archivo llamado exactamente Dockerfile (sin extensión, con D mayúscula) y copia el de la pestaña Kit. Crea también .dockerignore.
  2. Lee la tabla "línea por línea" del Kit. Fíjate en -DskipTests: en Render no existen tus claves durante la construcción, y la prueba contextLoads fallaría (como en el ejercicio 1). Las pruebas se corren en tu computadora.
  3. Revisa qué vas a subir: git status. Deben aparecer Dockerfile, .dockerignore y los .properties modificados. No debe aparecer datos/ ni ningún archivo con claves. Busca tu clave de Neon en todo el proyecto (en VS Code: Ctrl+Shift+F, pega npg_): cero resultados.
  4. Sube a la rama de trabajo y luego lleva los cambios a main con un Pull Request (Semana 4): 
    git checkout development
git add .
git commit -m "Prepara el despliegue: puerto flexible, perfil prod y Dockerfile"
git push origin development
# En github.com: Pull requests → New pull request → base: main ← compare: development → Create → Merge
✅ Checkpoint: en github.com, en la rama main, ves Dockerfile junto a pom.xml, y la búsqueda de npg_ en el repositorio no encuentra nada.

Ejercicio 8 — Verificación de punta a punta Nivel 4 · Rigor

📱 NAVEGADOR / CELULAR 🐘 NEON ☁️ RENDER

"Ya dice Live" no es lo mismo que "funciona". Un docente no da por aprendido un tema porque el estudiante dijo "sí entendí": le pide que lo demuestre. Aquí haces lo mismo con tu aplicación, con datos reales.

  1. Desde tu celular (con datos móviles, no el wifi de tu casa) abre tu dirección https://…onrender.com. Te lleva a /login, con el candado 🔒 en la barra.
  2. Escribe una clave incorrecta: "Usuario o contraseña incorrectos.".
  3. Entra como admin: ves a Diego (¡el que inscribiste desde tu PC en el ejercicio 5! Es la misma base).
  4. Inscribe un jugador nuevo, edítalo y elimina otro. Luego envía el formulario vacío y lee los dos mensajes de validación.
  5. Cierra sesión y entra como entrenador: no ves botones de gestión. Escribe a mano /jugadores/nuevo: "No tienes permiso…" (403).
  6. En Neon → Tables → jugador, refresca: los cambios que hiciste desde el celular están ahí.
  7. En Render: Manual Deploy → Restart service (o Deploy latest commit). Cuando vuelva a decir Live, recarga en el celular: los jugadores siguen. Esta es la prueba de que no estás usando H2.
  8. Cambia un texto pequeño (por ejemplo el título de lista.html), súbelo a development y haz el Pull Request a main. Mira la pestaña Events de Render: inicia un despliegue sin que toques nada.
  9. Deja la aplicación sin visitas más de 15 minutos y vuelve a abrirla: tardará cerca de un minuto en responder. No es un error: el plan gratuito "duerme" el servicio y lo despierta con la primera visita.
✅ Checkpoint: las nueve pruebas se comportan como se describe. Guarda capturas: son la evidencia de tu Entrega Parcial 3.
¿Y por qué ddl-auto=update y no algo "más profesional"?
En una empresa, los cambios a las tablas de producción se escriben a mano como "migraciones" numeradas (con herramientas como Flyway), se revisan y se aplican en orden, igual que un acta con cambios aprobados. update deja que Hibernate cree y amplíe las tablas por su cuenta: es cómodo para un proyecto escolar, pero nunca borra columnas viejas ni renombra con cuidado. Lo usamos a conciencia, sabiendo que en un sistema grande no sería suficiente.

5. Dockerfile nuevo en la raíz, junto a pom.xml

# ---------- Etapa 1: construir el .jar (una "cocina" con Maven y el JDK) ----------
FROM maven:3.9-eclipse-temurin-17 AS construccion
WORKDIR /app
COPY pom.xml .
COPY src ./src
# -DskipTests: las pruebas se corren en tu computadora; aquí no existen tus variables.

# ---------- Etapa 2: solo lo necesario para ejecutar (el "plato servido") ----------
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=construccion /app/target/*.jar app.jar
EXPOSE 8080
# MaxRAMPercentage: deja que Java use hasta el 75% de los 512 MB del plan gratuito.
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]
LíneaEn palabras de aula
FROM maven:3.9-eclipse-temurin-17 AS construccion"Consigue una cocina que ya tenga Java 17 y Maven instalados". La llamamos construccion.
WORKDIR /app"Trabaja dentro de la carpeta /app" (como hacer cd).
COPY pom.xml . y COPY src ./src"Mete los ingredientes": la lista de dependencias y tu código.
RUN mvn -B -DskipTests clean packageLo mismo que hiciste en el ejercicio 1, sin las pruebas. -B = sin colores ni preguntas (modo "lote").
FROM eclipse-temurin:17-jre"Ahora toma un plato limpio con solo Java para ejecutar" (JRE, sin Maven ni compilador: más liviano y con menos piezas que atacar).
COPY --from=construccion … app.jar"De la cocina, llévate solo el .jar". Todo lo demás se descarta.
EXPOSE 8080Una nota informativa. El puerto real lo decide server.port=${PORT:8080}.

Ojo con los tutoriales viejos: muchos videos usan FROM openjdk:17-jdk-slim. Esa imagen ya no existe en Docker Hub (fue retirada) y la construcción falla con not found. Usa las de este Kit (maven:3.9-eclipse-temurin-17 y eclipse-temurin:17-jre), comprobadas en octubre de 2026. Tampoco necesitas mvnw dentro de Docker: la imagen ya trae Maven, así evitas el clásico error de permisos de mvnw en repositorios hechos desde Windows.

Cómo provocarlo: terminal nueva, sin ADMIN_PASSWORD, y ./mvnw clean package.

Qué significa: la app usa el perfil dev escrito en application.properties y crea un H2 dentro del contenedor. Todo parece funcionar… hasta el siguiente despliegue o reinicio: el disco del contenedor se borra y los datos desaparecen. Neon sigue vacío.

Arreglo: arma las tres piezas como en el ejercicio 4. Si la clave apareció en un log o en una captura, cámbiala: Neon → Roles → menú de neondb_owner → Reset password, y actualiza DB_PASSWORD en Render.

Caused by: org.postgresql.util.PSQLException: ERROR: password authentication failed for user 'neondb_owner'

Ojo: si borras DB_PASSWORD, Spring no dice "falta la variable" (a diferencia de ADMIN_PASSWORD): envía el texto ${DB_PASSWORD} literal como contraseña, y Neon responde con este mismo mensaje. En los casos 3 y 4 (y en cualquier falla de conexión), el log termina siempre así:

Caused by: org.hibernate.HibernateException: Unable to determine Dialect without JDBC metadata (please set 'jakarta.persistence.jdbc.url' for common cases or 'hibernate.dialect' ...)

Qué significa: Hibernate dice "no pude hablar con la base, así que no sé qué tipo de base es". Es una consecuencia, no la causa. La regla de la Semana 13 ("lee el último Caused by") aquí no alcanza.

Arreglo: sube por el log y busca la primera línea con PSQLException o RuntimeException: Driver. Esa sí dice qué pasó (clave, formato de URL, servidor). No agregues hibernate.dialect: taparías el síntoma sin arreglar la conexión.

==> No open ports detected, continuing to scan... ==> Port scan timeout reached, no open ports detected

Qué significa: la app nunca llegó a encender Tomcat. Casi siempre es porque se cayó al arrancar (casos 2–5): busca el error más arriba en Logs. Mientras Spring arranca en el plan gratuito, ver un par de veces "continuing to scan" es normal.

Distinto: si la app ya estaba Live y la primera visita tarda ~1 minuto con una pantalla de carga de Render, está despertando (15 min sin visitas). No es un error: es el plan gratuito.

Qué significa: el usuario admin ya existe en Neon (lo creó el primer arranque, quizá desde tu PC en el ejercicio 5). CargadorUsuarios solo crea, no actualiza. En producción no puedes "borrar datos/": los datos están en Neon.

Arreglo: usa la clave original; o, si todavía no hay datos reales, en Neon → SQL Editor ejecuta DELETE FROM usuario; y en Render Manual Deploy → Restart service: los dos usuarios se recrean con las claves actuales. (Los jugadores no se tocan.)

Qué significa: aunque borres la línea y hagas otro commit, la clave queda en el historial de un repositorio público. Y los bots que buscan claves recorren GitHub en minutos.

Arreglo (en este orden): (1) cambia la clave en Neon (Reset password): la vieja deja de servir al instante; (2) pon la nueva en Render (Environment → Save, rebuild, and deploy); (3) quita la línea del archivo y haz commit. El paso 1 es el que protege; el 3 solo limpia.
