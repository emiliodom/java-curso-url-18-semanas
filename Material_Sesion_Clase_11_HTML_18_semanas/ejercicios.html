Cómo está armada esta escalera
Los ejercicios parten del módulo de registro que construiste la Semana 10 y lo van blindando una regla a la vez: primero compruebas el problema, luego lo arreglas, y al final lo haces accesible. Si tu módulo de la Semana 10 quedó incompleto, cópialo entero del Kit y sigue desde el Ejercicio 2.
Las tres preguntas ancla de esta semana
Cuando una validación "no funcione", revisa en este orden: (1) ¿agregaste la dependencia spring-boot-starter-validation al pom.xml? (2) ¿el método tiene @Valid antes del objeto y BindingResult inmediatamente después? (3) ¿la plantilla muestra los errores con th:errors?

Ejercicio 1 — Comprueba el problema Nivel 1

Ejecuta tu proyecto de la Semana 10 y registra a propósito un jugador imposible: deja el nombre vacío (o escribe un solo espacio) y pon 300 en la edad.

Tu turno: mira la lista. ¿Se guardó? ¿Qué le pasaría a la institución si esto ocurre cien veces?

✅ Checkpoint: viste con tus propios ojos que la aplicación acepta datos sin sentido. Ese es el problema que resuelve toda esta semana.
Solución
Se guarda sin protestar: el formulario nunca revisó nada. Un solo espacio pasa incluso si el campo tiene required en HTML, porque para el navegador "hay algo escrito". Por eso la validación de verdad se hace en el servidor.

Ejercicio 2 — Agrega la dependencia Nivel 1

En el pom.xml, dentro de <dependencies>, agrega el bloque del Kit (archivo 2) y ejecuta el proyecto una vez.

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

Tu turno: el proyecto arranca igual que antes y nada cambió a simple vista. ¿Para qué sirvió entonces?

✅ Checkpoint: el proyecto arranca con "Started ... Application" sin errores.
Solución
Sirvió para tener disponibles las anotaciones de validación y el motor que las ejecuta. Sin esta dependencia puedes escribir @NotBlank y el proyecto compila… pero no valida nada, en silencio. Es de los errores más difíciles de descubrir, porque no aparece ningún mensaje.

Ejercicio 3 — Tu primera regla Nivel 2

En Jugador.java, importa y anota solo el nombre:

import jakarta.validation.constraints.NotBlank;

@NotBlank(message = "El nombre es obligatorio.")
private String nombre;

Y en el controlador, activa la revisión (ojo al orden de los parámetros):

import jakarta.validation.Valid;
import org.springframework.validation.BindingResult;

@PostMapping("/jugadores")
public String registrarJugador(@Valid @ModelAttribute Jugador jugador,
                               BindingResult resultado) {
    if (resultado.hasErrors()) {
        return "formulario";
    }
    jugadorService.guardar(jugador);
    return "redirect:/jugadores";
}

Tu turno: envía el formulario con el nombre vacío. ¿Se guardó? ¿El usuario entiende qué pasó?

✅ Checkpoint: ya no se guarda el registro vacío.
Solución
No se guarda: el formulario simplemente vuelve a aparecer. Pero el usuario no tiene idea de por qué, porque todavía no mostramos el mensaje — eso es el Ejercicio 4. Es exactamente la mitad del trabajo: validar sin avisar es casi tan malo como no validar.

Ejercicio 4 — Muestra el mensaje Nivel 2

En templates/formulario.html, debajo de la casilla del nombre:

<p class="mensaje-error"
   th:if="${#fields.hasErrors('nombre')}"
   th:errors="*{nombre}">Mensaje de ejemplo</p>

Agrega también novalidate a la etiqueta <form> para que el navegador no bloquee el envío y puedas ver tu propia validación.

Tu turno: envía vacío otra vez. ¿De dónde salió exactamente el texto que aparece?

✅ Checkpoint: aparece tu mensaje en español debajo de la casilla.
Solución
Salió del message = "El nombre es obligatorio." que escribiste en la anotación del modelo. th:errors="*{nombre}" lo busca y lo escribe ahí. Si no pones message, Hibernate Validator usa uno genérico en inglés ("must not be blank"), que es justo lo que no queremos mostrarle a una persona.

Ejercicio 5 — Rangos y el cambio de int a Integer Nivel 3

Primero prueba el problema: con private int edad; todavía, deja la casilla de edad vacía y envía. Observa el error.

Ahora cámbialo a Integer y agrega las reglas:

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotNull;

@NotNull(message = "La edad es obligatoria.")
@Min(value = 5,  message = "La edad mínima para inscribirse es 5 años.")
@Max(value = 17, message = "Esta categoría admite hasta 17 años.")
private Integer edad;

Tu turno: ¿por qué con int el mensaje era feo y con Integer sí sale el tuyo?

✅ Checkpoint: con la casilla vacía sale "La edad es obligatoria."; con 300 sale el mensaje del máximo.
Solución
Un int no puede estar vacío: siempre tiene un número. Cuando llega "" del formulario, Spring intenta convertirlo, no puede, y genera un error técnico de conversión antes de llegar a tus reglas — por eso el mensaje es en inglés y habla de tipos.
Un Integer sí admite el valor nulo, así que la conversión funciona (queda en nulo) y entonces @NotNull se ejecuta y da tu mensaje.
Regla práctica: los campos numéricos que vienen de un formulario se declaran con Integer, Long o Double (con mayúscula), nunca con int/long/double.

Ejercicio 6 — Resumen arriba y casilla marcada Nivel 3

Agrega al inicio del formulario un resumen de todos los errores, y marca en rojo cada casilla que falló:

<div class="resumen-errores" role="alert" th:if="${#fields.hasAnyErrors()}">
    <p>Revisa estos datos antes de continuar:</p>
    <ul>
        <li th:each="error : ${#fields.allErrors()}" th:text="${error}">Error</li>
    </ul>
</div>
<input type="text" id="nombre" th:field="*{nombre}"
       th:errorclass="campo-error" />

Tu turno: envía el formulario con el nombre correcto y la edad inválida. Fíjate bien en la casilla del nombre: ¿se borró lo que escribiste?

✅ Checkpoint: aparece el resumen, la casilla con error se ve en rojo, y los datos correctos siguen escritos.
Solución
No se borró: como el controlador devuelve la plantilla (y no un redirect) con el mismo objeto, th:field vuelve a pintar los valores que el usuario ya había escrito. Esa es la diferencia entre un formulario que ayuda y uno que castiga. Si en vez de return "formulario"; hicieras return "redirect:/jugadores/nuevo";, se perderían los mensajes y todo lo escrito.

Ejercicio 7 — Hazlo accesible Nivel 3

Tres cambios pequeños en cada campo del formulario:

<label for="edad">Edad</label>
<input type="number" id="edad" th:field="*{edad}"
       th:errorclass="campo-error"
       aria-describedby="edad-error" />
<p id="edad-error" class="mensaje-error"
   th:if="${#fields.hasErrors('edad')}"
   th:errors="*{edad}">Error</p>

Tu turno: el for del label y el id de la casilla deben coincidir. Comprueba que funciona haciendo clic sobre el texto de la etiqueta: ¿qué pasa?

✅ Checkpoint: al hacer clic en la etiqueta se enfoca su casilla, y cada mensaje de error está ligado a su campo con aria-describedby.
Solución
El cursor salta a la casilla. Si no salta, el for y el id no coinciden — y eso significa que un lector de pantalla tampoco sabría de qué campo se trata.
aria-describedby="edad-error" le dice al lector de pantalla: "cuando leas esta casilla, lee también el texto que está en el elemento con id="edad-error"". Sin eso, el mensaje queda suelto y la persona no sabe a qué campo pertenece.
Agrega también role="alert" al resumen de errores: hace que el lector lo anuncie en cuanto aparece.

Ejercicio 8 — Reto: correo, teléfono y página de error Nivel 4

Agrega dos campos nuevos al modelo con sus reglas (ver Kit, archivo 3) y crea templates/error.html:

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Pattern;

@NotBlank(message = "El correo del encargado es obligatorio.")
@Email(message = "Escribe un correo válido, por ejemplo: nombre@correo.com")
private String correoEncargado;

@NotBlank(message = "El teléfono es obligatorio.")
@Pattern(regexp = "[0-9]{8}",
         message = "El teléfono debe tener exactamente 8 dígitos, sin espacios ni guiones.")
private String telefono;

Tu turno: ¿por qué @Email necesita además @NotBlank si ya "valida" el correo? Y visita una dirección inventada como /jugadoresss: ¿qué ves ahora?

✅ Checkpoint: los dos campos nuevos validan con tus mensajes, y una dirección inexistente muestra tu página de error, no la página blanca de Spring.
Solución
Porque @Email acepta el campo vacío: solo revisa el formato cuando hay algo escrito. Si quieres que además sea obligatorio, necesitas @NotBlank junto a ella. Es una pareja que casi siempre va junta.
Ojo con el caso contrario: @Pattern sí revisa la cadena vacía y la rechaza. Así que si un campo con @Pattern fuera opcional, habría que permitir el vacío en el propio patrón (por ejemplo regexp = "|[0-9]{8}", donde la primera alternativa es "nada").
La página de error aparece sola: Spring Boot usa templates/error.html automáticamente, sin configurar nada.

0. Tabla de anotaciones — con su paquete

Todas las anotaciones de validación vienen del paquete jakarta.validation.constraints, salvo @Valid (que está un nivel arriba, en jakarta.validation) y BindingResult (que es de Spring). Esta es la lista completa de lo que se usa esta semana:

AnotaciónImport completoQué exige
@NotBlankjakarta.validation.constraints.NotBlankTexto obligatorio: ni nulo, ni vacío, ni solo espacios
@NotNulljakarta.validation.constraints.NotNullQue el valor exista (para números, fechas, listas)
@Sizejakarta.validation.constraints.SizeLargo mínimo y máximo de un texto o lista
@Minjakarta.validation.constraints.MinValor numérico mínimo
@Maxjakarta.validation.constraints.MaxValor numérico máximo
@Emailjakarta.validation.constraints.EmailFormato de correo (acepta vacío: combínala con @NotBlank)
@Patternjakarta.validation.constraints.PatternQue el texto siga un patrón (teléfono, código, etc.)
@Validjakarta.validation.ValidEn el controlador: "revisa este objeto antes de entrar al método"
BindingResultorg.springframework.validation.BindingResultEn el controlador: el reporte de qué falló
Es jakarta, no javax
En tutoriales y videos viejos verás import javax.validation.constraints.NotBlank;. Eso era para versiones anteriores de Spring Boot. Tu proyecto usa Spring Boot 3, donde el paquete se llama jakarta. Si copias un ejemplo con javax, VS Code marcará el import en rojo y no compilará.

3. Jugador.java — el modelo con sus reglas lo modificas tú

Ruta: src/main/java/gt/edu/url/tallerformularios/model/Jugador.java

package gt.edu.url.tallerformularios.model;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

public class Jugador {

    @NotBlank(message = "El nombre es obligatorio.")
    @Size(min = 3, max = 40, message = "El nombre debe tener entre 3 y 40 caracteres.")
    private String nombre;

    // Integer, NO int: así la casilla vacía puede quedar nula y @NotNull da tu mensaje.
    @NotNull(message = "La edad es obligatoria.")
    @Min(value = 5,  message = "La edad mínima para inscribirse es 5 años.")
    @Max(value = 17, message = "Esta categoría admite hasta 17 años.")
    private Integer edad;

    @NotBlank(message = "Selecciona una posición.")
    private String posicion;

    // @Email acepta el campo vacío, por eso se acompaña de @NotBlank.
    @NotBlank(message = "El correo del encargado es obligatorio.")
    @Email(message = "Escribe un correo válido, por ejemplo: nombre@correo.com")
    private String correoEncargado;

    @NotBlank(message = "El teléfono es obligatorio.")
    @Pattern(regexp = "[0-9]{8}",
             message = "El teléfono debe tener exactamente 8 dígitos, sin espacios ni guiones.")
    private String telefono;

    // Constructor vacío: obligatorio para que el formulario funcione (Semana 10).
    public Jugador() {
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }

    public Integer getEdad() {
        return edad;
    }

    public void setEdad(Integer edad) {
        this.edad = edad;
    }

    public String getPosicion() {
        return posicion;
    }

    public void setPosicion(String posicion) {
        this.posicion = posicion;
    }

    public String getCorreoEncargado() {
        return correoEncargado;
    }

    public void setCorreoEncargado(String correoEncargado) {
        this.correoEncargado = correoEncargado;
    }

    public String getTelefono() {
        return telefono;
    }

    public void setTelefono(String telefono) {
        this.telefono = telefono;
    }
}
Se pueden poner varias anotaciones al mismo campo
La edad tiene tres (@NotNull, @Min, @Max) y se revisan todas. Si el usuario escribe 300, solo falla @Max y solo aparece ese mensaje. Cada anotación revisa una cosa y da su propio texto.

5. JugadorController.java lo modificas tú

Ruta: src/main/java/gt/edu/url/tallerformularios/controller/JugadorController.java

package gt.edu.url.tallerformularios.controller;

import jakarta.validation.Valid;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;

import gt.edu.url.tallerformularios.model.Jugador;
import gt.edu.url.tallerformularios.service.JugadorService;

@Controller
public class JugadorController {

    private final JugadorService jugadorService;

    public JugadorController(JugadorService jugadorService) {
        this.jugadorService = jugadorService;
    }

    @GetMapping("/jugadores/nuevo")
    public String mostrarFormulario(Model model) {
        model.addAttribute("jugador", new Jugador());
        return "formulario";
    }

    @PostMapping("/jugadores")
    public String registrarJugador(@Valid @ModelAttribute Jugador jugador,
                                   BindingResult resultado) {

        // BindingResult DEBE ir inmediatamente después del objeto validado.
        if (resultado.hasErrors()) {
            // Se devuelve la plantilla (NO redirect): así se conservan
            // los mensajes de error y lo que el usuario ya había escrito.
            return "formulario";
        }

        jugadorService.guardar(jugador);
        return "redirect:/jugadores";
    }

    @GetMapping("/jugadores")
    public String listarJugadores(Model model) {
        model.addAttribute("jugadores", jugadorService.listarTodos());
        model.addAttribute("total", jugadorService.contar());
        return "lista";
    }
}

8. templates/error.html nuevo esta semana

Ruta: src/main/resources/templates/error.html

Spring Boot usa este archivo automáticamente cuando ocurre un error no controlado (una dirección que no existe, por ejemplo). No hay que configurar nada: basta con que se llame error.html y esté en templates/.

<!doctype html>
<html lang="es" xmlns:th="http://www.thymeleaf.org">
<head>
  <meta charset="utf-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1" />
  <title>Ocurrió un problema</title>
  <link rel="stylesheet" th:href="@{/estilos.css}" />
</head>
<body>
<main>
  <h1>Escuela de Fútbol Los Cerritos</h1>

  <div class="resumen-errores" role="alert">
    <p><strong>No pudimos mostrar esta página.</strong></p>
    <p>Es posible que la dirección esté mal escrita o que la página ya no exista.</p>
    <p>Código del problema: <span th:text="${status}">404</span></p>
  </div>

  <p>
    <a th:href="@{/jugadores}">Ver la lista de jugadores</a> ·
    <a th:href="@{/jugadores/nuevo}">Inscribir un jugador</a>
  </p>
</main>
</body>
</html>
Qué mostrar y qué NO mostrar en una página de error
Sí: un mensaje en lenguaje normal, el código del problema y una salida (enlaces para seguir navegando). No: el detalle técnico del error ni la traza de Java — a la persona no le sirve y además revela cómo está hecho tu sistema por dentro.

9. application.properties

Ruta: src/main/resources/application.properties

spring.application.name=taller-formularios

# Mientras desarrollas: ver los cambios del HTML sin reiniciar el proyecto.
spring.thymeleaf.cache=false

# Permite que tu templates/error.html se use también para los errores 404.
spring.web.resources.add-mappings=true
server.error.whitelabel.enabled=false
La última línea desactiva la página blanca genérica de Spring, para que se use la tuya.
