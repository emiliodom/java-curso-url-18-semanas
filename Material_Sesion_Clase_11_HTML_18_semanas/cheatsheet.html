Referencia rápida — anotaciones, mensajes y errores

Tres pestañas: las anotaciones con su paquete completo, cómo mostrar los errores de forma clara y accesible, y el catálogo de errores frecuentes de esta semana.
Antes que nada: la dependencia
Ninguna anotación de esta pestaña funciona si falta este bloque en el pom.xml. Y lo peor es que no da error: el proyecto arranca y simplemente no valida.
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

A. Las anotaciones, con su import completo

AnotaciónImportQué exige y ejemplo
@NotBlank jakarta.validation.constraints.NotBlank Texto obligatorio: ni nulo, ni vacío, ni solo espacios.
@NotBlank(message = "El nombre es obligatorio.")
@NotNull jakarta.validation.constraints.NotNull Que el valor exista. Para números, fechas y listas.
@NotNull(message = "La edad es obligatoria.")
@Size jakarta.validation.constraints.Size Largo de un texto (o de una lista).
@Size(min = 3, max = 40, message = "...")
@Min jakarta.validation.constraints.Min Valor numérico mínimo.
@Min(value = 5, message = "...")
@Max jakarta.validation.constraints.Max Valor numérico máximo.
@Max(value = 17, message = "...")
@Email jakarta.validation.constraints.Email Formato de correo. Acepta el campo vacío, así que casi siempre va con @NotBlank.
@Email(message = "...")
@Pattern jakarta.validation.constraints.Pattern Que el texto siga un patrón.
@Pattern(regexp = "[0-9]{8}", message = "...")
@Valid jakarta.validation.Valid
(ojo: sin .constraints)		 En el controlador: "revisa este objeto antes de entrar al método".
BindingResult org.springframework.validation.BindingResult En el controlador: el reporte de qué falló. Es de Spring, no de Jakarta.
Es jakarta, no javax
Muchos tutoriales y videos en internet usan javax.validation..., que era el nombre en versiones anteriores. Tu proyecto usa Spring Boot 3, donde el paquete se llama jakarta. Si copias un ejemplo con javax, el import queda en rojo y no compila.

B. @NotNull vs @NotBlank vs @NotEmpty

Las tres suenan igual y no lo son. Esta tabla dice qué acepta y qué rechaza cada una:

Valor recibido@NotNull@NotEmpty@NotBlank
Nulo (la casilla no vino)RechazaRechazaRechaza
Texto vacío ""AceptaRechazaRechaza
Solo espacios " "AceptaAceptaRechaza
Texto con contenidoAceptaAceptaAcepta
Regla práctica para no equivocarse
Para texto que viene de un formulario, usa siempre @NotBlank (es la más estricta y evita el truco de escribir un espacio). Para números, fechas y listas, usa @NotNull, porque @NotBlank ni siquiera aplica a esos tipos.

C. Los dos detalles que hacen perder más tiempo

1. Campos numéricos: Integer, nunca int

private int edad;private Integer edad;
Si la casilla viene vacíaSpring no puede convertir "" a número → error técnico en inglésQueda en nulo → @NotNull da tu mensaje
Anotación que necesita(no alcanza a ejecutarse)@NotNull + @Min/@Max
Lo mismo aplica a Long en vez de long y Double en vez de double: en formularios siempre la versión con mayúscula.

2. El orden de BindingResult es obligatorio

// ✅ CORRECTO: BindingResult pegado al objeto validado
public String registrar(@Valid @ModelAttribute Jugador jugador,
                        BindingResult resultado,
                        Model model) { ... }

// ❌ INCORRECTO: hay un parámetro en medio → la aplicación truena
public String registrar(@Valid @ModelAttribute Jugador jugador,
                        Model model,
                        BindingResult resultado) { ... }
Si necesitas Model u otros parámetros, van después. La regla es: cada objeto validado lleva su BindingResult inmediatamente detrás, como una sombra.

A. Los ayudantes de Thymeleaf para errores

ExpresiónQué hace
th:errors="*{campo}"Escribe el mensaje de error de ese campo (el del message = "...").
th:errorclass="clase"Agrega esa clase CSS a la casilla solo si ese campo falló.
${#fields.hasErrors('campo')}¿Este campo tiene errores? Devuelve verdadero o falso.
${#fields.hasAnyErrors()}¿Falló algún campo del formulario? Sirve para el resumen de arriba.
${#fields.allErrors()}La lista de todos los mensajes, para recorrerla con th:each.

El patrón completo de un campo, tal como queda en la plantilla:

<label for="edad">Edad</label>
<input type="number" id="edad" th:field="*{edad}"
       th:errorclass="campo-error"
       aria-describedby="edad-error" />
<p id="edad-error" class="mensaje-error"
   th:if="${#fields.hasErrors('edad')}"
   th:errors="*{edad}">Texto de ejemplo</p>
#fields solo existe dentro del formulario
Estas expresiones funcionan dentro de la etiqueta que tiene th:object (o dentro del <form>). Si las usas fuera, Thymeleaf no sabe de qué objeto hablas y da error.

B. Accesibilidad: las cuatro reglas de hoy

ReglaCómo se haceA quién ayuda
Etiqueta asociada <label for="edad"> con el mismo texto que el id="edad" de la casilla Lectores de pantalla (anuncian de qué campo se trata) y cualquiera: al tocar la etiqueta se enfoca el campo
Error ligado al campo aria-describedby="edad-error" en la casilla, y ese mismo id en el párrafo del error Quien usa lector de pantalla: oye el mensaje junto al campo, no suelto al final
Aviso anunciado role="alert" en el resumen de errores El lector lo lee en cuanto aparece, sin que la persona tenga que ir a buscarlo
Nunca solo color Borde rojo y texto del error y un símbolo (▲) o la palabra "Error" Personas con daltonismo, y quien mira la pantalla bajo el sol
Y el foco visible
No quites el borde que aparece al navegar con la tecla Tab. Si el diseño no te gusta, cámbialo (outline: 3px solid #2563eb;), pero no lo elimines: quien no usa ratón se queda sin saber dónde está parado.

C. Cómo se escribe un buen mensaje de error

❌ Mensaje que no sirve✅ Mensaje que sí sirve
"Error""El nombre es obligatorio."
"must not be blank""El nombre es obligatorio."
"Dato inválido""El teléfono debe tener exactamente 8 dígitos, sin espacios ni guiones."
"Edad incorrecta""Esta categoría admite hasta 17 años."
"Formato de correo no cumple con el patrón""Escribe un correo válido, por ejemplo: nombre@correo.com"
La prueba de los tres segundos
Un buen mensaje responde, en tres segundos y sin tecnicismos: qué campo está mal, por qué, y qué hacer para arreglarlo. Si tu mensaje no responde las tres, reescríbelo. Y si el formato es raro (un teléfono, un código), muestra un ejemplo dentro del mensaje.

D. Buenas prácticas de UX en formularios

  • No borres lo que ya escribieron. Devuelve la plantilla, no un redirect. Es la regla número uno.
  • Marca el campo que falló, no solo un aviso general: en un formulario de ocho campos, "hay errores" no sirve de nada.
  • Di las reglas antes, no después. Si el teléfono son 8 dígitos, ponlo en la etiqueta: "Teléfono (8 dígitos)". Mejor prevenir el error que explicarlo.
  • Pide solo lo necesario. Cada campo extra es una oportunidad más de equivocarse y de abandonar el formulario.
  • Usa el tipo correcto de casilla (type="number", type="email"): en el celular aparece el teclado adecuado.
  • No presumas de la validación del navegador. Es una comodidad; la del servidor es la que protege de verdad, porque el navegador se puede saltar.

Errores de validación

Mensaje o síntomaQué significaCómo se arregla
🔇 Anoté el modelo pero no valida nada Falta la dependencia spring-boot-starter-validation, o falta @Valid en el controlador Revisa las dos cosas en ese orden. Son la causa del 90% de los "no me valida".
La aplicación truena al enviar el formulario BindingResult no está inmediatamente después del objeto validado Ponlo pegado al objeto; los demás parámetros (Model, etc.) van después.
