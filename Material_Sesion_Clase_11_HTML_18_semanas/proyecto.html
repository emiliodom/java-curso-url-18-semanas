Proyecto · Entregable de la Guía de Aprendizaje 11 (1 pt)

Tu formulario, ahora con validación y mensajes claros

Primero la guía paso a paso para validar el formulario de tu proyecto real, y al final la plantilla calificable. Fecha límite: antes de la Sesión 12 (3 de octubre de 2026). Esta semana no tiene Entrega Parcial — el siguiente hito es la Entrega Parcial 3, en la Semana 14.
Antes de empezar
Necesitas el módulo de registro de la Semana 10 funcionando (formulario que guarda + lista). Si quedó incompleto, recupéralo con el Kit de archivos completos, que trae los 9 archivos enteros con sus import.

Paso 0 — Decide TUS reglas antes de escribir código

Lo que se evalúa no es copiar anotaciones, sino que las reglas tengan sentido para tu institución. Antes de tocar Java, llena mentalmente esta tabla con tu entidad:

Campo¿Qué regla real tiene?Anotación
NombreObligatorio, y con un mínimo razonable de letras@NotBlank + @Size
EdadDepende de tu institución: una guardería no admite 40 años; un centro de adultos mayores no admite 5@NotNull + @Min + @Max
Teléfono8 dígitos en Guatemala, sin guiones ni espacios@NotBlank + @Pattern
CorreoCon formato válido (y obligatorio, si tu institución lo necesita)@Email + @NotBlank
Un campo de texto largoQue no exceda un máximo razonable@Size(max = ...)
Ejemplo de regla con sentido vs. sin sentido: en una guardería, @Max(value = 6) para la edad tiene sentido y demuestra que pensaste en tu institución. Un @Max(value = 999) puesto "por si acaso" no valida nada real. La rúbrica mira justamente eso.

Parte guiada — valida tu formulario

Paso 1 — Agrega la dependencia de validación

En tu pom.xml, dentro de <dependencies>:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
Si te saltas este paso, nada de lo demás funciona — y no da error
Sin esta dependencia puedes escribir todas las anotaciones que quieras: el proyecto compila, arranca y sigue guardando basura en silencio. Es el error más difícil de detectar de la semana.
✅ Checkpoint: el proyecto arranca con "Started ... Application" después de agregarla.

Paso 2 — Anota tu modelo con TUS reglas

Agrega los import y las anotaciones a tu clase de modelo. Recuerda cambiar los campos numéricos de int a Integer:

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

@NotBlank(message = "El nombre del niño es obligatorio.")
@Size(min = 3, max = 40, message = "El nombre debe tener entre 3 y 40 caracteres.")
private String nombre;

@NotNull(message = "La edad es obligatoria.")
@Min(value = 0, message = "La edad no puede ser negativa.")
@Max(value = 6, message = "La guardería atiende niños de hasta 6 años.")
private Integer edad;

Escribe tus propios mensajes en español: son los que va a leer una persona real de tu institución.

✅ Checkpoint: tu modelo tiene al menos 4 reglas repartidas en 3 campos distintos, y los campos numéricos son Integer.

Paso 3 — Activa la revisión en el controlador

Agrega los dos import y modifica tu método POST:

import jakarta.validation.Valid;
import org.springframework.validation.BindingResult;

@PostMapping("/ninos")
public String registrarNino(@Valid @ModelAttribute Nino nino,
                            BindingResult resultado) {
    if (resultado.hasErrors()) {
        return "formulario";      // devolver la plantilla, NO redirect
    }
    ninoService.guardar(nino);
    return "redirect:/ninos";
}
Dos reglas que no se pueden romper
(1) BindingResult va inmediatamente después del objeto validado; si pones otro parámetro en medio, la aplicación truena. (2) Cuando hay errores se devuelve la plantilla, no un redirect: el redirect borraría los mensajes y lo que el usuario escribió.
✅ Checkpoint: al enviar datos inválidos ya no se guarda nada (aunque todavía no se vean los mensajes).

Paso 4 — Muestra los mensajes en la plantilla

Para cada campo de tu formulario, debajo de su casilla:

<p class="mensaje-error"
   th:if="${#fields.hasErrors('nombre')}"
   th:errors="*{nombre}">Error</p>

Y un resumen al inicio del formulario, que ayuda cuando hay varios errores a la vez:

<div class="resumen-errores" role="alert" th:if="${#fields.hasAnyErrors()}">
    <p><strong>Revisa estos datos antes de continuar:</strong></p>
    <ul>
        <li th:each="error : ${#fields.allErrors()}" th:text="${error}">Error</li>
    </ul>
</div>

Agrega novalidate al <form> mientras pruebas, para que el navegador no bloquee el envío.

✅ Checkpoint: al enviar datos inválidos aparecen tus mensajes en español, debajo de cada campo.

Paso 5 — Hazlo accesible

Cuatro cambios pequeños, todos evaluados en la rúbrica:

  • Cada casilla con su <label for="..."> coincidiendo con el id.
  • aria-describedby en la casilla, apuntando al id del párrafo de su error.
  • role="alert" en el resumen de errores.
  • Estilos de error que no dependan solo del color: borde grueso, fondo distinto y un símbolo (▲) antes del mensaje. Copia el bloque de estilos.css del Kit (archivo 10).
✅ Checkpoint: al hacer clic sobre el texto de una etiqueta, se enfoca su casilla. Si no pasa, el for y el id no coinciden.

Paso 6 — Agrega tu página de error

Crea src/main/resources/templates/error.html con el nombre de tu institución y un enlace de regreso (modelo completo en el Kit, archivo 8). Agrega también en application.properties:

server.error.whitelabel.enabled=false
✅ Checkpoint: al visitar una dirección inventada aparece tu página, no la página blanca de Spring.

Paso 7 — Prueba como lo haría una persona real

Haz estas cuatro pruebas y anota qué ocurre en cada una (las vas a reportar en el entregable):

  1. Enviar el formulario completamente vacío.
  2. Enviar un valor fuera de rango (una edad imposible para tu institución).
  3. Enviar un dato con formato inválido (un correo sin arroba o un teléfono con letras).
  4. Llenar bien todo menos un campo, y comprobar que no se borra lo demás.
✅ Checkpoint: las cuatro se comportan como esperabas. La cuarta es la más importante de todas.

Paso 8 — Sube tu avance a GitHub

En tu rama development: commit con un mensaje descriptivo (por ejemplo "Agrega validación y mensajes de error al registro de niños") y push.

✅ Checkpoint: en GitHub.com se ven tu modelo anotado, tu controlador con @Valid y tus plantillas actualizadas.
