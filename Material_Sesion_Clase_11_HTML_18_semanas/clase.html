Semana 11 — Validación, errores y experiencia de usuario

Sábado 26 de septiembre de 2026 · 11:10–12:20 · En línea · Dominio de la demo: Escuela de Fútbol Los Cerritos (se continúa el formulario de la Semana 10). Los datos siguen en memoria; la base de datos es la Semana 12. Sin Entrega Parcial esta semana.

Objetivos (hoy)

  • Mostrar, con el formulario de la semana pasada, que hoy se guarda cualquier cosa.
  • Agregar la dependencia spring-boot-starter-validation.
  • Anotar el modelo con Bean Validation (@NotBlank, @NotNull, @Size, @Min, @Max, @Email, @Pattern), diciendo siempre de qué paquete viene cada una.
  • Activar la revisión con @Valid y leer el resultado con BindingResult, respetando su orden obligatorio.
  • Mostrar los mensajes en la plantilla con th:errors sin borrar lo que el usuario escribió.
  • Aplicar accesibilidad básica: label, aria-describedby, role="alert" y contraste.
  • Agregar una página de error propia (templates/error.html).

Normas rápidas

  • Cada anotación que aparezca en pantalla se dice con su paquete: "@NotBlank, de jakarta.validation.constraints".
  • Frase ancla de la sesión: "validar no es desconfiar del usuario, es ayudarlo a no equivocarse".
  • Regla que se repite tres veces porque siempre se olvida: BindingResult va inmediatamente después del objeto validado.
  • Cuando hay errores no se redirige: se devuelve la plantilla, porque el redirect borra los mensajes y lo que el usuario escribió.
Checklist antes de iniciar (docente)

  • Tener el formulario de la Semana 10 funcionando, para la demo de apertura.
  • Tener a mano el error de BindingResult mal colocado para mostrarlo a propósito (bloque 3).
  • Quien no tenga el módulo de la Semana 10 usa el Kit de archivos completos.

Guion minuto a minuto (70 min)

  1. Abre con la pregunta incómoda: "¿qué pasa si alguien inscribe a un jugador de 300 años, o deja el nombre vacío?". Deja que respondan antes de mostrar nada.
  2. Comparte el Quiz en modo Presaberes (4 minutos, individual).

Demostración de apertura (3 min). Con el proyecto de la Semana 10 corriendo, llena el formulario a propósito con basura y envíalo:

  • Nombre: (vacío, o un solo espacio)
  • Edad: 300

Muestra la lista: ahí está el registro, guardado tan campante. Esa imagen es la motivación de toda la sesión — no hace falta explicar más por qué se valida.

Agrega ahora la dependencia al pom.xml, dentro de <dependencies>:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
Por qué hace falta una dependencia aparte
Las anotaciones de validación no vienen con spring-boot-starter-web. Este Starter trae la implementación que las hace funcionar (Hibernate Validator). Si se anota el modelo sin agregarla, el proyecto compila y arranca… pero no valida nada, en silencio — un error de los que más tiempo hacen perder.

Paso 1 — anotar el modelo. Abre Jugador.java y agrega las reglas. Di el paquete en voz alta al escribir cada import:

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

public class Jugador {

    @NotBlank(message = "El nombre es obligatorio.")
    @Size(min = 3, max = 40, message = "El nombre debe tener entre 3 y 40 letras.")
    private String nombre;

    @NotNull(message = "La edad es obligatoria.")
    @Min(value = 5,  message = "La edad mínima para inscribirse es 5 años.")
    @Max(value = 17, message = "Esta categoría admite hasta 17 años.")
    private Integer edad;
    ...
}
El cambio de int a Integer hay que explicarlo, no esconderlo
Con int, si el usuario deja la casilla vacía Spring no puede convertir "" a número y produce un error técnico feo, antes de que tus reglas se ejecuten. Con Integer el valor puede quedar en nulo, y entonces @NotNull sí puede dar tu mensaje en español. Regla práctica: los campos numéricos de un formulario se declaran con Integer, no con int.

Paso 2 — pedirle a Spring que revise. En el controlador:

import jakarta.validation.Valid;
import org.springframework.validation.BindingResult;

@PostMapping("/jugadores")
public String registrarJugador(@Valid @ModelAttribute Jugador jugador,
                               BindingResult resultado) {
    if (resultado.hasErrors()) {
        return "formulario";        // vuelve al formulario con los datos y los errores
    }
    jugadorService.guardar(jugador);
    return "redirect:/jugadores";
}
PiezaPaqueteQué hace
@Validjakarta.validationLe ordena a Spring revisar las anotaciones del objeto antes de entrar al método.
BindingResultorg.springframework.validationEs el reporte de la revisión: qué falló y con qué mensaje.
Error que conviene provocar aquí (2 min)
Mueve BindingResult después de otro parámetro (por ejemplo Model model) y envía el formulario: la aplicación truena. BindingResult debe ir inmediatamente después del objeto validado, pegado a él. Es la regla que más se olvida, y el error no dice "cambiaste el orden".
Y por qué aquí NO se redirige
La Semana 10 terminó insistiendo en redirigir después de guardar. Hoy aparece la excepción: cuando hay errores se devuelve la plantilla (return "formulario";). Un redirect haría una petición nueva y en ella se perderían tanto los mensajes como lo que el usuario ya había escrito.

  • Estirar, agua, mirar lejos de la pantalla 20 segundos.
  • Micro-check en el chat: "¿de qué paquete viene @NotBlank?"

Hasta aquí ya no guarda basura, pero el usuario no ve por qué. Se arregla en la plantilla:

<label for="nombre">Nombre</label>
<input type="text" id="nombre" th:field="*{nombre}"
       th:errorclass="campo-error" />
<p class="mensaje-error" th:if="${#fields.hasErrors('nombre')}"
   th:errors="*{nombre}">Mensaje de ejemplo</p>
AtributoQué hace
th:errors="*{nombre}"Escribe el mensaje de error de ese campo (el que pusiste en message = "...").
th:errorclass="campo-error"Agrega esa clase CSS a la casilla solo si ese campo falló — para marcarla en rojo.
#fields.hasErrors('nombre')Pregunta si ese campo tiene errores; sirve para mostrar u ocultar el párrafo.
#fields.hasAnyErrors()Pregunta si algún campo falló; sirve para el resumen de arriba.
El momento clave de la clase: los datos NO se borran
Envía el formulario con el nombre bien escrito y la edad inválida. Señala en pantalla que el nombre sigue ahí: el usuario solo corrige lo que falló. Eso pasa porque se devolvió la plantilla con el mismo objeto, y th:field vuelve a pintar sus valores. Pregunta al grupo: "¿qué sentirías si un formulario largo te borrara todo por un dato malo?" — esa es la parte de experiencia de usuario del programa.

Agrega también el resumen de errores al inicio del formulario, que ayuda cuando la página es larga:

<div class="resumen-errores" role="alert" th:if="${#fields.hasAnyErrors()}">
    <p>Revisa estos datos antes de continuar:</p>
    <ul>
        <li th:each="error : ${#fields.allErrors()}" th:text="${error}">Error</li>
    </ul>
</div>
Truco para la demo: novalidate
Si el formulario conserva los required del HTML, el navegador bloquea el envío y nunca se ve la validación del servidor. Agrega novalidate a la etiqueta <form> durante la clase para poder demostrarla. Explica que las dos validaciones conviven: la del navegador es comodidad, la del servidor es la que de verdad protege los datos.

Tres mejoras cortas, en este orden:

MejoraCómoPor qué
Etiquetas bien asociadas<label for="edad"> con el mismo valor del id de la casillaQuien usa lector de pantalla oye qué casilla es; además, al tocar la etiqueta se enfoca el campo

Conexión con su rol docente (vale 1 minuto)
Nombra que esto no es decoración: en un aula real habrá estudiantes con baja visión o daltonismo. Las mismas tres reglas que aplican hoy (etiqueta clara, mensaje que dice qué hacer, no comunicar solo con color) son las que después van a necesitar al preparar materiales para sus propios grupos.

Página de error propia. Crea src/main/resources/templates/error.html: Spring Boot la usa automáticamente, sin configurar nada, cuando ocurre un error no controlado (por ejemplo una dirección que no existe).

Cierre del bloque
Visita a propósito una dirección inventada (/jugadoresss) y muestra que ya no aparece la página blanca genérica de Spring, sino una con el nombre de la institución y un enlace de regreso. Es un cambio pequeño con un efecto enorme en la percepción del usuario.

  1. Comparte el Challenge: pestaña 1 "Elige la validación correcta" y pestaña 2 "Simulador: ¿qué pasa al enviar?".
  2. Modela una vez el escenario "datos inválidos" del simulador (2 min): se ve que la petición nunca llega al servicio y que la plantilla se devuelve con los datos intactos.
  3. Resuelven por su cuenta y exportan el PDF (evidencia de la Actividad en clase junto con el quiz).
